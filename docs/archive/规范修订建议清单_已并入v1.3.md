## 0. 一句话结论

v1.2 把审稿设定为「每周 15 分钟人工」；按每周 4 篇算是**每篇 3.75 分钟**，而 §8.3 要求"每个数字必须实时搜索官方源"、§8.5 要求"至少 5 个精确数字带来源"。

**3.75 分钟里人不可能逐个核对来源。** 所以 v1.2 的"人工审稿"实际上已经是一道橡皮图章——它给出的是**安全感**，不是**数据准确性**。

本次修订的动作因此不是"删掉一道有效防线"，而是**把一道无效的防线换成两道有效的机器闸门**：

| | v1.2 | v1.3 建议 |
| :--- | :--- | :--- |
| 发布前把关 | 人工看观点/英文（3.75 分钟） | **智能体质检**（硬规则、可失败、可阻断构建）+ **信息增量闸门** |
| 发布后把关 | 无明确机制 | **GSC 数据回流**：曝光/点击/query 异常反查质检与选题 |

**但有一个前提必须写进规范正文**：机器闸门只能保证"不出错"，**不能保证"有价值"**。删掉人工审稿后，唯一还能提供"价值"的机制是**自有成本模型的计算输出**。这一条不落实，本方案会退化成规模化内容滥用（见第 5 节风险 R1）。

## 1. 统一方法论（三项目共用一套，本节建议单独抽成跨项目文件）

现状是三个项目三套方法论，这是最根本的问题。建议把方法论从"某个项目的规范"里抽出来，变成**跨项目共用的一份**，各项目只写"差异说明"。

### 1.1 方法论内核（四层闭环，项目无关）

```
① 选题数据层   数据源 → 目标词 + 搜索意图 + 信息增量假设
                          （产出：选题卡，含"这篇比 SERP 前三多什么"）
        ↓
② 生产层       模板 + 参数化模型 → 初稿
                          （产出：Markdown + 结构化 frontmatter）
        ↓
③ 质检闸门层   独立智能体 + 硬规则 + 信息增量校验
                          （产出：pass / fail；fail 不允许发布）
        ↓
④ 数据回流层   GSC 曝光·点击·query → 优化 / 合并 / 淘汰 / 新选题
        ↓                                   （回到 ①）
```

### 1.2 三条不可妥协的原则

1. **写稿智能体与质检智能体必须分离。** 同一个上下文里"自己检查自己"等于没有检查。质检智能体只看**产物 + 官方源**，不看写稿时的推理理由。
2. **每个数字必须机器可校验。** 数值 + 单位 + 时间 + 具名来源 + 抓取日期，五元组缺一不可；抓不到来源就标"待核实"，且**待核实状态不允许发布**。
3. **每篇文章必须有信息增量。** 定义：SERP 前三名页面上**没有**的元素（自有计算、独家口径、GSC 自有数据、可追溯的一手来源交叉验证）。做不到就不写这篇。

### 1.3 三项目如何统一

建议新建 `METHODOLOGY_v1.md` 放在三个项目都能访问的位置，各项目规范里只保留一张映射表：

| 层级 | 本项目（英文内容站） | 项目 B（GlobalPoetAI?） | 项目 C（欧越曼?） | 差异原因 |
| :--- | :--- | :--- | :--- | :--- |
| ① 选题数据层 | Google Trends / Reddit / GSC / 长尾词 | 待填 | 待填 | |
| ② 生产层 | V6.1 六段模板 + 成本模型库 | 待填 | 待填 | |
| ③ 质检闸门层 | 15 条硬规则（本文 §2.2） | 待填 | 待填 | |
| ④ 数据回流层 | GSC 周报 → 改 title/desc/淘汰 | 待填 | 待填 | |

> **需要你提供**：GlobalPoetAI、欧越曼、SPARTA-Pro 的现有文档。这三个名字不在本仓库，也不在我可见的上下文里，我无法判断它们的层级映射是否成立，也无法判断 SPARTA-Pro 是否已经定义了 E-E-A-T 四层——如果已经定义，应当**对齐它**而不是另起一套。

## 2. 详细修订条目（v1.2 → v1.3）

### R1｜删除人工审稿（§9 整节重写）

**原文**：AI 写完后发到飞书文档，你看观点/补经历/看英文/说"发"；你的时间投入：每周 15 分钟。

**建议改为**：

```
§9 发布闸门（v1.3）

发布不依赖人工审稿。文章从 status: drafting 进入 status: published
的唯一路径是：通过智能体质检（§9.1）并满足信息增量闸门（§9.2）。

人工不参与单篇放行。人工的可选介入点只有两个：
  · 例外仲裁：智能体判定为"来源冲突"（同一数字两个官方源不一致）时
  · 定期校准：见 §9.3
```

**理由**：3.75 分钟/篇不具备核对能力，保留它只会让人误以为数据被核对过——**虚假的安全感比没有防线更危险**。

**副作用（必须承认）**：观点质量、英文地道度、"这篇值不值得发"这三个判断，将不再有人做最终裁决。应对方式见 §2.2 规则 10/11/13 与第 5 节 R1/R5。

### R2｜新增「智能体质检」规范（全新章节）

**位置**：建议作为 v1.3 §9.1，替代原 §8.5 的 15 项人工清单（清单本身保留，但改为机器执行）。

**质检智能体的设计约束**：

- 与写稿智能体**不同会话、不同系统提示**，理想情况不同模型；
- 只接收：文章 Markdown、frontmatter、以及联网抓取的官方源页面；
- **不接收**写稿智能体的推理过程或"我为什么这么写"的说明；
- 输出必须是结构化的逐项结论（pass / fail / warn + 证据），不是散文式点评。

**质检规则表（v1.3 建议稿）**：

| # | 检查项 | 判定方式 | 失败等级 |
| :--- | :--- | :--- | :--- |
| 1 | 数字五元组完整（数值+单位+时间+具名来源+抓取日期） | 逐数字解析，缺项即失败 | **阻断** |
| 2 | 来源可验证（质检体实时抓官方源比对数值） | 抓不到 → 标"待核实" | **阻断** |
| 3 | 模糊词清零（may / might / possibly / perhaps / could / reportedly / allegedly） | 正则扫描 | **阻断** |
| 4 | AI 套话清零（"In today's fast-paced world" / "delve" / "landscape" / "it's important to note" / "unlock the secrets"…） | 词表扫描，可扩展 | **阻断** |
| 5 | AI Summary 存在且 40–60 词，直接回答主题 | 计数 + 判定 | **阻断** |
| 6 | 六段结构完整（Hook / What happened / Why now / So what / For you / Data point） | 标题匹配 | **阻断** |
| 7 | FAQ 3–5 问，答案 80–150 词（见 R5） | 计数 | **阻断** |
| 8 | Comparison Table ≥1、Definition Block ≥1 | 结构解析 | **阻断** |
| 9 | 字数 1500–2500 | 计数 | **阻断** |
| 10 | 正文无 URL（只标信源名称） | 正则 | **阻断** |
| 11 | 免责声明存在 | 字符串匹配 | **阻断** |
| 12 | 政策时间线存在（追溯 2–3 年） | 结构匹配 | 警告 |
| 13 | 分人群建议 ≥3（新卖家/品牌卖家/套利卖家） | 结构匹配 | 警告 |
| 14 | **信息增量 ≥1**（见 §2.2 闸门） | 抓 SERP 前 3 名逐项比对 | **阻断** |
| 15 | **站内查重**：与已发布文章相似度低于阈值 | 向量/文本相似度 | **阻断** |
| 16 | **关键词唯一性**：targetKeyword 未被站内其他文章占用 | 查选题池 | **阻断** |
| 17 | 敏感词黑名单（政策红线 §12） | 词表 | **阻断** |
| 18 | Schema 完整性（Article + FAQPage + BreadcrumbList + Organization） | 构建期校验 | **阻断** |
| 19 | 英文门禁（Bloomberg/FT 风格重写；逐字翻译痕迹检测） | 生成式重写，非阻断 | 自动修 |
| 20 | 可读性指标（句长、被动语态比例、词频） | 统计 | 警告 |

**「阻断」的工程含义**：`status` 无法置为 `published`；CI 直接失败；文章不进 sitemap、不进 RSS、不出现在首页。也就是**机器闸门替代了人的最后一句话**。

### R3｜新增「信息增量闸门」（§9.2，本次修订最关键的一条）

> **状态（2026-10-01）：已实现。** 落地为 `tools/serp-check.mjs`，四种声明类型全部可机检，官方源自动排除出竞品分母，抓不到即返回 INCONCLUSIVE、绝不返回 PASS。SERP 来源可插拔（`--serp=bing` 或 `--serp=file:<快照>`），因为本机无法从 Google/DuckDuckGo 抓取、Bing 会截断查询。用法：`pnpm qa:serp`。详见 README「发布前自检」。

这一条是"取消人工审稿"能成立的**唯一前提**。

**定义**：发布前，质检体抓取目标词 SERP 前 3 名页面，逐项比对，要求本文至少命中以下一项：

- **A. 自有计算**：文章包含一个用自有成本模型算出的结果（FOB → 关税 → 平台费 → 到手成本），前三名没有；
- **B. 自有口径**：多个官方源交叉验证后得出一个前三名没做的比较（例如同一政策在两国税则下的差异）；
- **C. 自有数据**：来自 GSC 的真实 query 数据或读者行为数据（第一年只有这一项，产生较晚）；
- **D. 一手来源直读**：直接从官方原文/公告/统计库取值，且明确标注抓取日期，前三名引用的是二手转述。

**四项都不命中 → 不发布。** 不是"改一改再发"，是**这篇选题作废**。

**理由（官方依据）**：Google 的 spam 政策把 **scaled content abuse** 定义为 *"many pages generated for the primary purpose of manipulating search rankings and not helping users"*，举例明确包含 *"using generative AI tools to generate many pages **without adding value** for users"*。注意句式：违规 = **many pages + without adding value**，两个条件去掉任一个都在政策之外。删掉人工审稿后，"many pages"这一侧已经拉满，**唯一能守住的就是"adding value"**。

### R4｜修正 GSC Indexing API（§2 技术架构表 + §7.1 均需改）

**原文**：`→ 自动提交 GSC Indexing API`（§2）、`部署后自动提交 GSC Indexing API`（§7.1）。

**事实**：Google 官方文档明确，Indexing API **只能用于 `JobPosting` 与 `BroadcastEvent`（直播视频）两类页面**，且需要 service account + 配额审批，滥用会被吊销配额。普通文章不在支持范围内。

**建议改为**：

```
§2 … → Cloudflare Pages 自动构建部署
     → GSC 提交 sitemap（一次性）+ lastmod 保持准确
     → Bing 提交 IndexNow（推送新 URL）
     → 每周拉 GSC 数据 → 选下周选题
```

**补充一条 v1.2 缺的认知**：AI 引用的入口不只有 Google——

| 引擎 | 检索来源 | 你能做的 |
| :--- | :--- | :--- |
| ChatGPT / Copilot | Bing 索引 | **IndexNow 推送 Bing**（免费） |
| Claude | Brave Search | 被动，靠第三方提及 |
| Perplexity | 自家爬虫 + 强偏好近 12 个月内容 | 保持发布节奏与 `updatedDate` |
| Google AI Overviews | Google 自身排名 | 传统 SEO 依然是前置条件 |

结论：**"只盯 Google"会漏掉一半 AI 引用入口**，IndexNow 是 v1.2 完全没有、但成本几乎为零的一步。

### R5｜修正 FAQ 规范（§7.2）

**原文**：使用 FAQ 结构（8-12 个问答）。

**两个问题**：

1. **Google 已于 2026-05-07 正式下线 FAQ 富媒体摘要**（商业站早在 2023-08 就已不显示）。FAQPage schema **从来不是排名因素**。所以"用 FAQ 换搜索展现"这个预期是错的。
2. **算术冲突**：8-12 问 × 80-150 词的推荐答案长度 = 640-1800 词，加上六段模板的 1500-2500 词，总量会失控。

**建议改为**：

```
§7.2 FAQ 规范（v1.3）
· 目的：为 LLM 引用服务，不为富媒体摘要（Google 已下线该展现）
· 数量：3-5 问
· 答案长度：80-150 词（短答案在 ChatGPT/Perplexity 中被引用率更低）
· 保留 FAQPage schema（schema 仍有效，读取方从 Google 转为 LLM）
· 期望管理：不要以"拿到富媒体摘要"为验收标准
```

**依据**：Google 于 2026-05-07 停止展示 FAQ 富媒体摘要；2026-06 退役 Search Console 报告，2026-08 移除 API 支持。且 FAQPage schema 保留有效，主要阅读方已变为 LLM。

### R6｜Frontmatter 字段定稿（§5 重写）

v1.2 §5 的字段与已建成的仓库实现是两套。**绝不能两套并存**（同一篇文章两套字段名会导致静默丢失校验）。建议以**并集**定稿：

```yaml
---
# —— 内容 ——
title: "..."                      # ≤120 字符
excerpt: "..."                    # ≤300 字符，同时用作 meta description 与卡片摘要
date: "2026-09-29"                # 采用 v1.2 命名
updated: "2026-10-05"             # 可选；Perplexity 偏好新鲜度，此字段要真用
category: "trade-policy"          # ← 用 slug，不用显示名（见下方说明）
tags: ["tariffs", "landed cost"]

# —— 选题与质检（v1.3 新增，全为必填）——
target_keyword: "TikTok Shop China seller requirements 2026"
search_intent: "informational"    # informational | transactional | comparison
information_gain: "custom-calculation"   # custom-calculation | cross-source | own-data | primary-source
status: "published"               # idea | drafting | needs-review | verified | published
qa:                               # 质检智能体回写，人工不填
  checked_at: "2026-09-29"
  ruleset_version: "v1.3"
  result: "pass"
  blocked_rules: []

# —— 数字与来源（v1.3 新增，§8.3 的机器化）——
figures:
  - value: "15.7"
    unit: "%"
    period: "2026-08"
    source: "National Bureau of Statistics, industrial profits release"
    retrieved: "2026-09-28"
sources:
  - "Ministry of Commerce of the PRC, press conference, 2026-09-29"
  - "General Administration of Customs, trade statistics, 2026-08"

# —— 作者与媒体 ——
author: "V"
hero_image: "/images/xxx.png"     # 见 R8
youtube_id: ""                    # 可选，见 R13
priority: "P0"                    # P0 | P1 | P2
featured: false
draft: false
---
```

**`category` 用 slug 而不是显示名的理由**：显示名一旦改动（例如 "Trade Policy" → "Trade & Tariffs"），200 篇历史文章的 frontmatter 全部要改；用 slug 只需改一处显示映射。v1.2 目前写的是显示名 `"Trade Policy"`，建议改。

### R7｜目录与 URL 定稿（§3）

| 项 | v1.2 | 已建成仓库 | **v1.3 建议** | 理由 |
| :--- | :--- | :--- | :--- | :--- |
| 内容目录 | `src/content/posts/` | `src/content/blog/` | **`src/content/posts/`** | 跟规范；posts 更中性，未来可容纳非 blog 内容 |
| URL 前缀 | `/posts/...` | `/blog/...` | **`/posts/...`** | URL 是唯一发布后就改不动的东西（需 301），现在定死 |
| 内容配置 | `src/content/config.ts` | `src/content.config.ts` | **`src/content.config.ts`** | Astro 5+ 起官方位置已变更，旧位置会告警 |
| 建站命令 | `npm` | `pnpm`（已验证可构建） | **pnpm** | Cloudflare Pages 两者都支持，但要写死一个；pnpm 的 lockfile 更严格 |

> 目录与 URL 的改名成本：**现在改 = 改两个字符串；发布后改 = 写重定向 + 丢权重**。这一条建议在写第一篇之前定死。

### R8｜图床决策修正（§2 技术选型表 + §7.3）

**原文**：图床用 Cloudflare R2 或外部图床，理由是"图片不进 Git 仓库"。

**先算量级**：200 篇 × 1 张封面（1200×630），按每张 200KB 算是 **40MB/年**。Git 对此毫无压力（GitHub 单文件上限 100MB、仓库软上限 1GB）。

**而代价是真实的**：图片放外部图床，会丢掉 Astro 构建期的图片优化（AVIF/WebP 转换、`srcset`、尺寸推导、LQIP）；Cloudflare 的图片优化（Image Resizing / Images）是**付费项**。

**建议**：
- **封面图放仓库**，交给 Astro 构建时优化；
- **只有视频与多图素材放 R2**（视频不占仓库这条是对的，保留）；
- 若每篇要配 3-5 张 AI 图（一年 600-1000 张、200-500MB），再切到 R2 + 自定义 image service。

> **所以这条取决于：每篇计划几张图？**（见第 7 节待拍板）

### R9｜发布节奏写成硬约束（§10.2 与 §15 的统一）

**原文冲突**：§10.2 说"一年 200 篇"，§15 说"❌ 一次性堆几百篇文章"。

**建议改为**：

```
§10.2 发布节奏（v1.3）
· 每周 3-4 篇，质量优先
· 任何一周因质检未通过而少于 3 篇，不补发、不顺延堆积
· 禁止批量灌稿：单日发布上限 1 篇
· 年度总量不作为 KPI（总量目标会诱发赶工，赶工直接击穿数据防线）
```

### R10｜KPI 换轨（新增章节）

**原来隐含的 KPI 是访问量**。在前 AI 搜索时代这是对的，现在不是：AI Overview 出现时传统结果 CTR 下降约 61%。

**建议主指标改为三项**（按优先级）：

| 指标 | 为什么 | 采集方式 |
| :--- | :--- | :--- |
| 1. **订阅数** | 唯一你真正拥有、且不会被 AI 摘要截走的资产 | 邮件服务后台 |
| 2. **GSC 曝光量**（不是点击） | 曝光代表被索引、被理解；点击由 AI 决定 | GSC 周报 |
| 3. **被 AI 引用次数** | GEO 是否真的成立 | 每月手工跑 15-20 个 prompt 记录 |

辅助指标：被索引页面数、每篇 30 天是否拿到曝光（这是质检有效性的反查信号，见 §4）。

**行为影响**：订阅应在第一天就成为首要资产，而不是 v1.2 §13 里"2 年后"的变现路径。每篇结尾要给出"值得订阅"的**具体理由**，而不是"喜欢就订阅"。

### R11｜重写"人工痕迹"条款（§8.1）——零人工审稿下的必然推论

v1.2 §8.1 要求的"第一人称经验"，在**没有人提供经历**的前提下，只能由 AI 编造。必须改写：

| 元素 | v1.2 | **v1.3 建议** |
| :--- | :--- | :--- |
| 精确数字 | ≥5 个，带数值+单位+时间+来源 | 保留，但升级为**五元组 + 机器校验**（R2/R6） |
| 成本测算 | ≥1 个，FOB×税率×柜量 | 保留，且**必须来自成本模型库**（§3），不接受即兴计算 |
| 第一人称经验 | "I've been..." | **改为"分析师追踪陈述"**：只允许可由公开数据支撑的观察（"Tracking this since 2024, three of four adjustments followed the same sequence"）。**禁止任何无法核实的具体个人经历与金额** |
| 明确观点 | Don't do X. Do Y. | 保留（可自动生成，但需附推理依据） |
| 反常识点 | Most sellers think X, but actually Y | 保留，但 X 必须是**有出处的大众认知**，不能是编造的稻草人 |
| 分人群建议 | 新卖家/品牌卖家/套利卖家 | 保留，由成本模型按参数化输出三档 |

**新增硬红线（建议写入 §12）**：

> 任何具体金额、损失数字、客户案例、样本量，若无公开可核实的来源，**一律不得出现在正文中**。包括但不限于"我们追踪了 XXX 家店铺""我 2021 年亏了 $40,000"。

**这条为什么重要**：现有仓库里的 6 篇占位样例中就出现过我编造的"412 家美国 TikTok Shop 店铺样本""268 家 Temu 店铺样本"。这正是零人工审稿＋数据驱动组合下**最典型的产物**，也是必被 AI 引擎交叉验证拦下的类型。

### R12｜"待核实"必须有工程后果（§8.3 强化）

**原文**：搜不到就标"待核实"，绝不编造。

**建议补一句工程约束**：

```
§8.3 数据防线（v1.3）
· 数字五元组不完整 → 构建失败
· 质检体抓不到官方源 → 自动标"待核实"
· status 含"待核实"数字的文章 → 不允许置为 published（硬阻断）
· "待核实"数字超过 2 个 → 该选题退回选题池，等待来源
```

### R13｜视频明确延后（§6 保留但标注阶段）

§6 的视频规范写得完整且方向正确（`youtube-nocookie`、懒加载、不占仓库、必须含真实录屏或声音）。**但 §16 第一阶段目标里没有视频，这是对的。**

**建议**：§6 标注为 **P5 阶段启用**。视频是第二条独立产线（脚本、录制、剪辑、字幕、封面），在单篇流程尚未稳定前引入，会先把节奏撑爆。

### R14｜删除 §9 的"飞书审稿"，但保留飞书的另一个用途

取消审稿后，飞书从"审稿台"变成 **选题池 + 状态看板**：选题卡在飞书多维表，`status` 变更由质检结果驱动。v1.2 的选题表字段（§10.1）保留，并**并入 R6 的字段集**。

## 3. 新增章节：成本模型库（v1.3 §11 建议）

**这是把"人工经验"替换为"自有模型"的关键资产，也是信息增量（R3-A）的供给源。**

### 3.1 是什么

一组参数化的计算脚本 + 一张参数表，输入品类/货值/目的地/平台，输出标准成本表，文章直接引用其输出。

### 3.2 建议覆盖的参数

| 类别 | 参数 |
| :--- | :--- |
| 关税 | 目标国 HS 编码税率、MFN/加征/反倾销叠加规则、原产地规则 |
| 平台费 | Amazon referral / FBA 配送与仓储；Temu 全托管与半托管；TikTok Shop 佣金与履约 |
| 物流 | 海运整柜/拼柜单价区间、空运单价、体积重换算、旺季附加费 |
| 资金 | 汇率、账期、库存周转天数对应的资金成本 |
| 退货 | 各品类退货率区间（须标来源） |

### 3.3 为什么它是本方案的支柱

1. **提供信息增量**：SERP 前三名通常没有可复现的成本模型，只有定性描述；
2. **保证口径一致**：同一条海运线在两篇文章里不会出现两个单价；
3. **把每篇的"成本测算"从 30 分钟降到 2 分钟**——这是产能的真正来源，而不是"让 AI 写快一点"；
4. **可被质检体校验**：模型输出可复算，编造的数字复算不出来。

## 4. 数据回流闭环（v1.3 §10.3 建议新增）

发布后按周拉 GSC，按下表自动判定并生成动作：

| 信号 | 判定 | 自动动作 |
| :--- | :--- | :--- |
| 有曝光 · 无点击 | 标题/描述不吸引 | 生成 title/description 改写候选，走 A/B |
| 有排名 · 曝光极低 | 索引或抓取问题 | 检查是否被索引、sitemap 是否收录、内链是否指向 |
| 点击尚可 · 停留差 | 内容与搜索意图不匹配 | 重写 AI Summary 与 Hook |
| 30 天零曝光 | 选题错 **或** 质检失效 | **先重跑质检体**：质检通过 → 判为选题问题，退回选题池；质检失败 → 判为质检漏检，进规则修订 |
| 出现未瞄准的新 query | 意外的真实需求 | 直接进下周选题池 |
| 某篇被 AI 引用 | GEO 命中 | 反向拆解：它命中了哪条信息增量，复制到同类文章 |

**第 4 行是本方案的自校准机制**——它部分替代了被删掉的人工抽检：不需要人读文章，而是用"零曝光"这个客观信号去反查质检是否失效。
