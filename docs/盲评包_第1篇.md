## 二、评分表怎么填（每项的写法）

每一格都是三件事：**分数 / 引用位置 / 一句理由**。

示例（**这是格式示范，不是对本文的评分**）：

```
conclusion = 2
引用：## What happened 第 1 段 "The wage floor for employees in Malaysia is RM1,700 a month"
理由：结论在首段给出，但 "did not arrive everywhere on the same day" 之后的表述比证据支持的范围更宽。
```

## 七、交回之后：如何变成一条真实记录

评审者交回上表后，由**非评审者本人**（编辑）把它转成 JSON，写入 `data/reviews/`。字段一一对应：

| 表单 | JSON 字段 | 规则 |
|---|---|---|
| reviewer_id | `reviewer_id` | 化名；真实映射不放仓库 |
| reviewed_at | `reviewed_at` | ISO 日期 |
| review_type | `review_type` | `blind` 需同时满足下一行 |
| 四项确认 | `blind_to` | **必须**恰好包含 `["prompt_version","model","traffic","other_reviews"]`，少一项评估器会标记为"不可信的盲评" |
| 六项分数 | `scores.{conclusion,sourcing,mechanism,malaysia_impact,uncertainty,actionability}` | 未评的写 `null`，**不要写 0** |
| N/A 理由 | `na.{key}` | `scores` 为 `null` 时必须有句子 |
| 红线五格 | `red_lines.{key}` | 布尔值，未触发写 `false` |
| 红线说明 | `red_line_notes[]` | 触发时必填：句子 + 证据 + 处理建议 |
| 问题清单 | `issues[]` | 每项 `{criterion, problem, evidence, suggested_fix}` |
| 首次评审 | `revision` | 写 `{"before":null,"after":null,"revised_at":null}` |
| 文章标识 | `article_id` | `malaysia-minimum-wage-rm1700-order-2024` |
| 语言 | `locale` | `en` |
| 来源真实性 | `provenance` | **`observed`**（真实评审）|
| 测试标记 | `fixture` | **`false`** |
| 提示词版本 | `prompt_version` | **`null`**——本篇写于版本常量之前，不得倒填 `writer-2026-10-26.a` |

**JSON 骨架（照抄后逐项填，不要放进 `data/reviews/` 之前留空字段）：**

```jsonc
{
  "review_id": "rev-2026-10-27-001",
  "article_id": "malaysia-minimum-wage-rm1700-order-2024",
  "locale": "en",
  "reviewer_id": "r-<化名>",
  "reviewed_at": "2026-10-27",
  "prompt_version": null,
  "review_type": "blind",
  "provenance": "observed",
  "fixture": false,
  "scores": { "conclusion": null, "sourcing": null, "mechanism": null, "malaysia_impact": null, "uncertainty": null, "actionability": null },
  "na": {},
  "red_lines": { "unsourced_key_fact": false, "unverifiable_number": false, "fabricated_interview": false, "prediction_as_fact": false, "stale_source": false },
```

## 八、复评（修改后）

1. 按 `issues[]` 修改文章；
2. **同一位评审者**再评一次，填写 `revision.before`（首次分数）与 `revision.after`（本次分数）；
3. 只有 **before 与 after 都存在**才算配对；只有一处则视为一次新评审，不计算改善幅度。
4. 配对记录少于 20 条时，评估器输出 `insufficient`，不给出"平均提升 X 分"这种结论。

## 九、人工执行步骤（真实评审 → 数据库）

| 步 | 谁 | 动作 | 完成标志 |
|---|---|---|---|
| 1 | 编辑 | 把本文件 + 文章 + 评分表交给评审者；**不**附提示词版本、模型、流量、他人评分 | 评审者确认收到且未看到四项 |

| 3 | 编辑 | 转成 JSON，`provenance: observed`、`fixture: false` | 文件写入 `data/reviews/` |
| 4 | 编辑 | 运行 `node tools/eval-loop.mjs --editorial` | 看到 records=1、observed=1，六项均为 `insufficient (n=1)` |
| 5 | 编辑 | 揭示四项元数据，与评审者讨论差异 | 讨论记录附在 PR/提交说明里（不进 `data/reviews/`） |

## 十、一致性核对（评分表 ↔ 评估器）

| 评分表 | JSON | 评估器行为 |
|---|---|---|
| 六项 0–3 | `scores.*` | 分项均值，**从不合成总分**；`null` 排除并计入 missing |
| 允许 N/A 且须理由 | `na.*` | 计入 `N/A with reason` 并单列，不按 0 分 |
| 五类红线 | `red_lines.*` | 按类型计数；触发即列出文章 id |
| 盲评四项 | `blind_to` | 缺任一项 → 标记 `suspect blind`，不当作盲评 |
| 评审者间差异 | 同文章 ≥2 名不同评审者 | 否则输出 `not computed` 与原因 |
| 复评前后 | `revision.before/after` | 只有配对才计算；<20 对 → `insufficient` |
| 不得把点击当质量 | 无流量字段 | 编辑报告完全不读流量数据 |

### 已知歧义（记录，不擅自改 schema）

1. **`actionability` 的 N/A 边界**：评分表允许解释性稿件填 N/A；但"解释性"与"没有可执行建议"的界线由评审者判断，评估器不做语义检查。→ 处理：`na` 理由必须写清是哪一种情况。
2. **`stale_source` 与 `reviewBy`**：文章有 `reviewBy: 2027-02-01`，但"最新数据已过期"由评审者按来源自身的发布日期判断，系统不自动比对。
3. **盲评的"看不见流量"是流程承诺，不是技术强制**：仓库里没有流量数据，评审者也拿不到；但系统无法证明一个人没有在别处查过。→ 处理：以 `blind_to` 声明 + 编辑流程留痕为准。
4. **复评的分差方向**：评估器同时输出 `before`/`after` 与差值，但不判断"变好"；分数下降也可能是评审更严格。→ 处理：解读需人工，报告里不写"改善"字样。
