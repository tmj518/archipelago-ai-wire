## 一之三、开工前自检 `tools/preflight.mjs`（2026-10-06 新增，学自另一个项目）
**来源**：另一个流水线（豆包那个美方项目）的 `preflight.py`。它的做法是**跑之前先自检**，并且**对我们踩过的坑用不同标记单独标出**。我们照抄了这个机制。

### 它解决什么

**本项目的环境问题，全部是"跑到一半才发现"的。** 第四节 D 组是历史坑表，而**光 2026-10-03 一天就新增 5 个**（E1–E5）。**这五个没有一个难检测——它们只是从来没在开工前被检查过。**

```powershell
node tools/preflight.mjs                    # 只查环境
node tools/preflight.mjs --profile=daily    # 加查该档位的依赖，并给就绪判断
node tools/preflight.mjs --init             # 初始化档位状态文件
node tools/preflight.mjs --done=daily       # 记录一次成功运行（更新 next 时间）
node tools/preflight.mjs --json             # 给脚本用
```

### 两个设计要点（别改回去）

**① 缺凭据不算失败。** 写文章不需要 R2 token，也不需要 YouTube OAuth。**凭据只报"未配置"，不影响退出码**——只有该档位**真正需要**的东西才能判失败。

> **一个因为没用的能力而变红的前检，会被忽略；被忽略的前检比没有更糟。**

**② 能用"做一次"验证的，就不用"文件存在"验证。** `python -c "import edge_tts"` 是证据，`Test-Path python.exe` 不是。所以检查项是**真跑一次**。

### 检查项对着我们自己的坑表写

| 检查 | 对应坑 |
| --- | --- |
| python（**并验证能 import edge_tts / Pillow**） | 内置 runtime python **没有** edge_tts，独立 Python 3.13 才有 |
| ffmpeg / ffprobe | 视频与播客渲染 |
| **proxy 127.0.0.1:7890 在监听** | D10 |
| **HTTPS 通不通（用 node fetch 探，不是 curl）** | **E1** —— 用 curl 探会报错层 |
| curl.exe https（单独报，提醒它不可靠） | E1 |
| **git remote（`git ls-remote` + 重试）** | **E4** |
| qa-check 能不能跑 | 闸门本身失效就不会有人发现 |

### 实测：它当天就抓到一次真故障

第一次跑时 `git auth` 报 `ssh: connect to host github.com port 22: Connection timed out`——**而 20 分钟前同一项还是绿的**。这正是它存在的意义。

**同时暴露了我的第一个版本检测方法错了**：`ssh -T` 探的是 **22 端口**，而**推送可能走 443**，且本机 github 访问**本来就是间歇性中断**（路线图 §2.1 记录过）。**用 22 端口判"能不能推"会误报。**

**已改成**：探 `git ls-remote origin main`（走远端真实配置的路径），**并重试一次**（这里的失败模式是丢包，不是确定性失败），失败时提示"这是间歇性的，下结论前先重试"。

### 三个命名档位（对应规范 §8 的节奏）

```
daily     每天 07:00   发最多 1 篇：写稿 → 双闸门 → 提交 → 推送 → 线上核验
weekly    周一 14:00   GSC 拉数 → 闸门自检 → 选题池刷新
monthly   每月 1 日 09:00   方向判断（加倍哪个栏目）+ updated 回改清查
```

**状态文件**：`build/state/profiles.json`（在 gitignore 的 `build/` 里，**属于机器状态，不是项目内容**）。记录每个档位的 `lastRun`，据此算 `next`。

> **⚠️ 一个我自己写的 bug，已修**：`next` 时间原本用 `toISOString()` 显示，**输出的是 UTC**，而调度是用 `setHours()` 算的**本地时间**。本机 UTC+8，所以 **07:00 的那次运行显示成前一天 23:00**——全部差 8 小时。**已改成显示本地时间**（`localStamp()`），因为**人要照着它行动的是墙上时间**。

### 为什么用"就绪时间"而不是硬编码 cron

它记录**上次什么时候跑的、下次什么时候该跑**。这对我们有用，因为**我们的 `updated` 回改机制**（待办第 10 项）本质就是"到期该回改"——**出口退税篇 2027-01-01 有硬截止**，正是需要"就绪时间"的东西。

**总判断**：**这是一个"站"的骨架，不是"产线"的骨架。**
**它最大的特征是——没有 `tools/`。** 而我们有 **26 个脚本**（11 个成本模型 + 4 个闸门/自检 + 5 个取数 + 5 个发布产物），**那才是这个项目真正值钱的部分**。规范说护城河是"算"，一个只有 `src/` 的框架描述不了"算"。

## 一之五、计算透明度小节（2026-10-06，待办第 19 项完成）

### 动机：这是竞品案例给我们的唯一真缺口

**NapLab 的壁垒有一半来自"公开怎么测的"**（10 项标准测试、43-64 个数据点、评分规则全写明），读者能验证所以能信任。

**我们做等价的工作，但读者看不到**：

| 我们有的 | 读者看得到吗 |
| --- | --- |
| `figures[]` 五元组 | ❌ **只在 frontmatter 里** |
| 成本模型 `tools/*.mjs` | ❌ **读者不知道模型存在** |
| 第 14 篇那张"每个输入都印出来"的表 | ✅ 但**是偶然做的，不是规范要求的** |

### 改动

**新增小节 `## How we calculated this`**，位置在 **The data point 之后、The point 之前**（先给结论，再给方法）。

**V6.1 的章节顺序因此变为**：

```
AI Summary → What happened → Why now → So what → For you → The data point
→ (How we calculated this) → The point → FAQ
```

> **注意**：这个新小节 **不在 `qa-check` 的 `SECTIONS` 强制列表里**，因为它**只对 `custom-calculation` 的文章适用**——一篇纯 `primary-source` 的稿子没有自有算术可公开。**加进强制列表会让不适用的文章被迫凑一节。**

### 新闸门规则（`qa-check.mjs`）

**只对 `information_gain: custom-calculation` 的文章生效**：

- **BLOCK**：声明了 `custom-calculation` 但没有 `## How we calculated this` 小节
- **BLOCK**：有小节但没有围栏代码块（公式或模型输出）
- **WARN**：有公式但正文没点出读者自己的输入项

**规则设计上犯过一次错并修正**：第一版把"点出读者输入"也做成 **BLOCK**，判据是一串关键词（`input|cif|value per unit`）。结果**三篇文章因为写了 "the spend is yours" / "unit FOB value is the input" 而失败**——**那是在考词汇，不是在考能不能验证。**

**已改成**：**围栏代码块是硬证据**（公式摆出来了），"是否用了某个词"降为 WARN。**和 primary-source 那条规则同一精神：声明某事，就必须能在正文里找到证据——但证据是实质，不是措辞。**

### 落地范围

**14 篇已发布全部补齐**（13 篇新增 + CBAM 篇把原有公式块挪进新小节并去掉了「So what」里重复的推导）。

**CBAM 那篇卡了字数**（正文硬上限 2500，它原本 2494，加小节后 2604）→ 逐段削减措辞，**数字一个没动**，最终 2498 词通过。

### "回改"是什么（明确一下，因为容易被误解成删除或重写）

**不是删除，不是整篇重写。是定点更新过期的那部分，并公开标注改动。**

| | 现在（2026-10） | 2027-01-01 之后 |
| --- | --- | --- |
| 出口退税篇说的 | 电池退税 9%→6%，**2027-01-01 归零** | 已归零 |
| 每件成本 | $1.20（3 个点） | **$2.40（6 个点）** |

### 一个真缺口：机制只保证"有人看"，不保证"看了会改"

**Google 要的是内容变化，不是日期变化。** 公开立场明确：**只改日期不改善排名**（John Mueller），而且**只刷日期不换内容是 Google 点过的操纵行为**。依据：[Changing Dates on Pages Won't Improve Rankings](https://www.searchenginejournal.com/googles-john-mueller-changing-dates-on-pages-wont-improve-rankings/401734/)、[Updating a Page's Publishing Date Won't Make it Rank Better](https://www.searchenginejournal.com/google-updating-a-pages-publishing-date-wont-make-it-rank-better/314833/)、[Updating XML Sitemap Dates Doesn't Help SEO](https://www.searchenginejournal.com/googles-john-mueller-updating-xml-sitemap-dates-doesnt-help-seo/545547/)。

**所以 `reviewBy` 触发的动作必须是"改内容或明说无需改"，绝不是"更新日期"。** 否则机制退化成刷日期。

**核实过的现状**（别凭印象）：

```
对外显示 updatedDate        无
JSON-LD dateModified        无
```

**即：`updatedDate` 这个字段现在哪儿都没用。** 即使改了它，Google 也收不到信号。

### 诚实结论：这个机制不产生外部收益

**它对 Google 没用，对用户不可见。它是内部保险，不是增长手段。**

按 KPI 顺序（订户数 > GSC 曝光 > AI 引用）：订户 **0**、GSC **0**、AI 引用**有一点**（引用一个过期价格比不引用更糟）。

> **别把它算进增长计划。它买的是"防止失分"。**

**还有一条反噬风险**：如果把复查日期露给用户（"Last reviewed: …"），用户看到一个**一年前**的日期，会理解成**"这站没人管"**。**除非它总是很新，否则是自曝其短。**

### 后续（待办 22，等决定）

**能同时讨 Google 和用户喜欢的是另一样东西**：**可见的真实修订记录**（"2027-01-05 更正：电池退税已归零"）+ **`dateModified` 进 JSON-LD**。

**关键区别**：**接的必须是真实修订（`updatedDate`），不是复查时钟（`reviewBy`）。** 前者是真实信号，后者是刷日期。

## 一之八、真实修订记录（2026-10-07，待办第 22 项）

### 为什么必须和 `reviewBy` 分开

**用户已明确要求写进流程**：

> **"`reviewBy` 触发的动作应该是'改内容或明说无需改'，绝不是'更新日期'。否则机制会退化成刷日期。"**

**理由（已核实）**：Google 的公开立场是**只改日期不改善排名**，而且**只刷日期不换内容是被点过的操纵模式**。**所以：**

| | 用途 | 能否进对外可见字段 |
| --- | --- | --- |
| **`reviewBy`** | **复查时钟**（我们内部） | ❌ **绝不能** —— 接进 `dateModified` 就是把"计划复查日"伪装成"修订日" |
| **`updatedDate` / `revisions`** | **真实修订**（内容真的变了） | ✅ 这才是能给 Google 和用户的真信号 |

### 用户要的东西

> **"这不仅是 SEO 有效，而且是唯一能让用户看见我们'还在管'的东西——比任何 'Last reviewed' 标签都可信，因为它写的是改了什么。"**

**所以可见的不是"最近复查于"，而是"改了什么"。**

---

### 实现

**新字段 `revisions`**（frontmatter，schema 已加）：

```yaml
revisions:
  - date: 2026-10-02
    note: "An earlier version described the cancelled schedule as covering photovoltaic products. ..."
```

| 组件 | 作用 |
| --- | --- |
| **`revisions` 字段** | 结构化记录"改了什么"，`note` 限 20-600 字 |
| **`ArticleLayout` 渲染 `Corrections and updates`** | 位置在 Sources 之后、相关阅读之前；**无修订记录时整节不渲染** |
| **JSON-LD `dateModified`** | **取最新一条修订的日期**，没有修订就不输出该字段 |
| **闸门规则** | 修订日期不能早于 `publishDate` = **BLOCK**；`updatedDate` 与最新修订不一致 = **WARN** |
| **`VERBOSE=1`** | qa-check 现在能列出**通过的**规则（否则只能看到失败） |

### 三个关键决定

**① `dateModified` 来自 `revisions`，不来自 `updatedDate`，更不来自 `reviewBy`。**
**这是"不刷日期"的机械保证**——审计 `[slug].astro` 时可以看到 `dateModified` 只读 `data.revisions.at(-1)`。**`reviewBy` 接进去就是伪造修订。**

**② 无修订记录时整节不渲染。**
**"Last reviewed: …"这种常驻标签必须显示一个日期，而一个一年前的日期读起来是"这站没人管"——它在替我们自曝其短。** 所以只显示"改了什么"，没改就什么都不显示。

**③ 日期不进 byline。**
**否则每篇文章的署名行都会随修订变动**——那就又变成刷日期了。

### 回填

**出口退税篇**：它**原本在正文末尾有一段散文式更正说明**（"*Correction, 2 October 2026: ...*"），是 2026-10-02 我发现"光伏退税取消"应更正为"249 个产品行"时加上的。

**那段已移进 `revisions` 字段并从正文删除**——**同一处内容不出现两次**。验证了页面上该更正文本**恰好出现 1 次**。

> **这也说明模式一直存在，只是纯手工、没有结构、还要写进正文才能看见。** 结构化之后：单一来源、固定渲染位置、机器可读、可校验。

**其余 13 篇不填 `revisions`**——**没有可核实的修订就不编。** 只有能追溯到 git 记录或本次会话真实改动的才写。

### 一个"看不见通过项"的问题，已修

**qa-check 原来只打印 BLOCK 和 WARN，pass 一律不打印。** 结果是：**"某条规则通过了"和"某条规则根本没运行"从外部无法区分。**

**这正是我在这个会话里踩了 6 次的同一个坑**（检查器比被检查对象更脆）。**已加 `VERBOSE=1`**，可列出通过的规则。实测：

## 一之九、视频产线扩展到全部文章（2026-10-07，待办第 9 项）

### 现状核实

**产线本来就是通用的**——`build_scenes(slug)` 从 `src/content/blog/<slug>.md` 读内容，**没有任何针对单篇的硬编码**。所以"扩展"= **逐篇跑通 + 修掉暴露的问题**。

### 跑了全部 14 篇，暴露一个真缺陷

```
14 篇全部可渲染，coverage 98-101%
但连续调用时 14 次里有 2 次失败：edge_tts NoAudioReceived
```

**报错信息是误导的**：

> `No audio was received. Please verify that your parameters are correct.`

**它会让你去查声音名和语速**——而真实原因是**服务端限流/瞬时抽风**。**两条失败的都在几秒后重跑就成功了。**

### 修了三处

**① 加重试 + 抖动退避**
4 次尝试，延迟 `2^(n-1) × 1.5 + random(0,1)`（**加抖动是因为触发条件是限流，固定延迟会二次碰撞**）。全部失败时报**真实原因**，并明确说"通常是限流，先等一分钟重跑，别改参数"。

**② 临时文件 + 成功后改名**
原来 `with open(audio_path,"wb")` **直写目标文件**——**失败会留下一个被截断的 .mp3，下一阶段会照样把它合进视频**。现在写 `.part`，成功才 `replace()`。

**③ 只重试传输错误，不重试代码错误**
第一版用 `except Exception` 全捕。**测试注入一个坏替身时抛了 `TypeError`，结果被重试了 3 次**——**`TypeError` 说明代码写错了，重试只是在掩盖 bug。** 现在只捕 `edge_tts` 异常族 + `EmptyAudioStream` + `OSError` + `TimeoutError`，其余第一次就抛。

**空流也算可重试**：连接建立但没发数据，是服务抽风而不是调用方参数错。**这条是测试抓出来的**——原本它抛普通 `RuntimeError`，不在重试列表里，一次就死。

## 一之十一、关键词通路诊断（2026-10-07，待办 6/8 的前置）

### 结论先说：**通路没坏，坏的是排序信号**

**我一开始也以为网络坏了**（之前的记录写"矿工的 HTTPS 是坏的"）。**实测不是。**

| 检查 | 结果 |
| --- | --- |
| `.curlrc` | ✅ 存在，含 `proxy` + `ssl-no-revoke`，**并写明这条路径丢 1/3 到 1/2 请求**（成功率 50-75%） |
| `curl.exe` 直连 Google Suggest | ✅ **正常返回**（实测拿到真实候选） |
| 矿工实跑 | ✅ `suggest 65 次 / bing 65 次 / call failures: google 0, bing suggest 0` |

**真正的瓶颈是两个缺失的凭据 + 一个被吞掉的失败计数。**

### ⚠️ 我做错的一件事（重要）

**我先看到 Bing 的"SOAP/POX API 于 2026-08-31 退役"公告，又看到我们代码里是 `api.svc/json/GetKeywordStats`，就推断"端点是死的、要迁移"。**

**读完来源才发现完全相反**：

| 协议 | 状态 |
| --- | --- |
| `/api.svc/soap` | 退役 |
| `/api.svc/**pox**/METHOD` | 退役 |
| **`/api.svc/json/METHOD`** | **✅ 继续支持——"这就是目的地"** |

**我们用的正是第三个。端点无需改动。** 依据：[Bing Webmaster 公告](https://www.bing.com/webmasters/about?setlang=zh-cn)、[迁移说明](https://crawlraven.com/blog/bing-webmaster-tools-api-retirement)、[GetKeywordStats 参考](https://bing-webmaster-api.analyticsedge.com/getkeywordstats/)。

> **教训（新增 C13）**：**看到一个相似的模式（`api.svc`）就推断结论，而没读完那一句。** 那句话是"**只有 `/soap` 或 `/pox/` 会坏**"——**我把"这三个端点里有两个死了"读成了"这套 API 死了"。**

### 修的三处

**① 保留全部候选池（真数据丢失）**

**第一次运行：`scored 139 candidates, selected 12` —— 另外 127 个只出现在一行日志里，永久丢失。**

**这在我们的场景下是错的取舍**：列表是给人挑的，而入选的 12 个是按 `hit_count` 排的，**在降级批次里这个信号很弱**（见下），**弱到不足以支撑"把其余的扔掉"**。

**现在**：`candidates_<stamp>.csv` 保留全部已评分候选。**实测 383-395 行**（对比之前只留 12 行）。

**② 报"单次调用失败数"（防止失败被摘要吞掉）**

**第一次运行：摘要写 `source failures: 0`，而日志里有 26 条 `suggest failed`。** 因为这个计数器**只统计"进入了入选行的失败"**。

**现在**：额外报 `call failures: google N, bing suggest N, bing stats N` + `calls made`，并在有失败时明确说"**这是部分批次，不是干净批次**，即使每一行看起来都完整"。

**③ 检测"排序退化"（最关键的一条）**

```
实测分布: hit_count {"1":373, "2":22}   ← 没有 3
```

**原因**：`hit_count` 满分 3，**GSC 未配置 → 每行最多到 2**；**无 Bing key → `monthly_volume` 全为 `-`**。

**后果**：排序函数的三级键（hit_count → volume → **关键词长度**）**全部落到最后一级**。**所以那份"精选 12 条"实际是按关键词长度排的。**

**而这个事实在所有计数器里都看不出来**——运行报零失败、看起来健康，**而输出不携带任何"哪个词重要"的信息**。

**现在**：工具会明确打印

```
!! RANKING IS DEGENERATE — the shortlist order carries no signal.
   distinct hit_count values: 2; volume data present: false
   Every comparison falls through to 'shorter keyword first'. Do not
   treat the top of this list as the best opportunities.
```

### 所以"用数据选题"这件事**还没实现**，缺的正是两样凭据

| 缺什么 | 影响 |
| --- | --- |
| **`BING_API_KEY`** | 没有绝对搜索量 → 排序第二级键失效 |
| **GSC 凭据** | `hit_count` 上限被压到 2 → 排序第一级键基本失效 |

> **两样都缺时，工具仍然能跑、仍然输出几百个候选、仍然"零失败"——但它给你的顺序是假的。**
> **这正是"运行成功 ≠ 数据可用"的第二个实例**（第一个是 2026-10-02 那次）。

### 闸门缺陷 A：`serp-check` 的"具名来源"数错了对象

**`namedSources` 原判据**：`(body.match(/^>\s+\*\*/gm) || []).length`——数**正文里的粗体引用块**。

**但粗体引用块是"定义块"**，`qa-check` 要求每篇 ≥1 个，**而库里 15 篇全部恰好 1 个**。所以这个值**恒为 1**，而 `cross-source` 规则要求 ≥2 → **任何 `cross-source` 文章都必然 UNSUPPORTED**。

**为什么一直没炸**：**14 篇已发布全是 `custom-calculation` 或 `primary-source`，只有 `cross-source` 会读这个数。** 第 15 篇是**第一篇 `cross-source`**，于是立刻报

> `article does not show at least two named sources`

**而它 frontmatter 里有 6 个 `sources` + 8 个各带 source 的 `figures`。**

**根因：一个字段名承载了两种含义。** 定义块规则要的是引用块数，cross-source 规则要的是来源数——**它们从来不是同一个量**。

**已修**：`namedSources` 改为数 frontmatter 的 `sources[]` 条目 + `figures[]` 里不重复的 `source:` 值；引用块计数另存为 `definitionBlocks`。

**回归实测**：**15 篇用各自已存的 SERP 快照重跑，15/15 `SUPPORTED`**，修复无副作用。

## 一之十三、需求代理指标：**实测后放弃**（2026-10-07）

### 我的假设

**闸门说"搜索需求必须另行验证"，而我们没有任何需求数据，所以选题一直靠判断。** `BING_API_KEY` 能给绝对搜索量但未配置。

**我提议的做法**：用免费的 Google Suggest 构造一个弱信号——**一个短语出现在多少个不同种子的建议里、以及排在多前**。**我打算叫它 `demand_proxy`，绝不叫"搜索量"。**

### 实测：两个前提全部不成立

```
seeds answered        12/12
distinct phrases      120        ← 12 个种子 × 10 条 = 120，去重后仍是 120
phrases under 2+ seeds 0 (0.0%)  ← 跨种子重复率是零
best-rank 分布         {"0":12,"1":12,...,"9":12}   ← 每个位置恰好 12 次
```

**① "广度"没有变化量**：**短语从不跨种子重复**。12 个不相关的种子产出 120 个互不重叠的短语——**"出现在几个种子里"永远是 1**。

**② "位置"没有变化量**：每个位置恰好 12 次，是因为每个种子返回恰好 10 条。

**→ 这个指标是装饰品。放弃，不建。**

> **如果我不先做这个实证，就会建一个看起来像指标的指标**，而它的每个值都是常数。**这正是"运行成功 ≠ 数据可用"的第三类变体：指标能算出来 ≠ 指标承载信息。**

### 顺带发现的真事实：Suggest 会把种子原样回波

**rank 0 恰好 12/12 次**这个模式促使我单独测了一次，**结果是部分成立，而不是普遍成立**：

```
seeds answered       12/12
seed echoed at rank 0  8/12
seed echoed anywhere  10/12   (位置: 0,0,0,0,1,0,0,0,1,0)
```

**不回波的两个恰好更有信息**：

```
"steel quota"  → "steel quota canada"      ← 真实查询，不是字面量
"china export" → "china exports"           ← 只差一个复数
```

**还撞到一个噪音证据**：

```
"customs" → "customs map tarkov"           ← 电子游戏内容
```

> **所以 `suggest[0]` 是一个弱信号，不能当发现。** `keyword-miner` 已有的种子回波过滤（`isRelevant` 丢弃种子自身）是**必要的**——这一点被证实，而不是被推翻。

### 结论：**在没有凭据的情况下，Suggest 给不了需求数据**

**矿工文档里那句话是对的**：

> **"Bing Webmaster 是唯一能给出绝对搜索量数字的来源。"**

**而 `GetKeywordStats` 需要 key。** 所以：

> **要"用数据选题"，`BING_API_KEY` 是绕不过去的。** 没有它，我们能得到的只有候选清单和一条**退化到按关键词长度排序**的伪排序（见"§ 关键词通路诊断"）。

**这条调查到此关闭，且已记录理由，避免以后重复尝试。**

## 一之二十九、一条我要固化成规定的教训：**不要对构建产物 grep 字面量**

```

**看实际产物 → 模式切换代码完整且正确。**

### 三次同类失败，根因都是我没搞清压缩器会改什么

| # | 我 grep 了什么 | 压缩器实际做了什么 | 结果 |
| --- | --- | --- | --- |

| 2 | 同一个标识符 | **重命名局部函数**为 `e` | 假失败 |
| 3 | `addEventListener("click"` | **把引号规范成反引号** | 假失败 |

### 规定

> - **要测事件绑定** → 测 `addEventListener` 与事件名**分开匹配**，不匹配完整调用式
>

## 一之三十二、第 19 篇：**一个只落在钢上、不落在铝上的工具**（2026-10-07）

```

```

> **所以决定采购决策的比较，不是碳的那两个数字。**

### 值得发表的那个发现：**交叉点是一个数**

```

CBAM（热轧卷）= 固定 €163.53/吨

```

| CIF/吨 | 配额关税 | CBAM | 谁大 |
| --- | --- | --- | --- |
| €300 | €150.00 | €163.53 | **CBAM** |
| €700 | €350.00 | €163.53 | 配额关税 **2.14 倍** |
| €1,000 | €500.00 | €163.53 | 配额关税 **3.06 倍** |

**而翻倍本身就是一个可比的数量**：CIF €700 时，从 25% 到 50% **加了 €175/吨**——**比同一批钢的全部碳费（€163.53）还多。**

  其中基准值扣除贡献      €3.89
  其中排放默认值贡献      €822.25
```

> **机制并没有更严厉地对待铝——只是铝的默认排放值是钢的四倍**（因为生产它排放更多）。

> 手机上打开网址，Menu 按钮点击没反应？

**复现了。但原因不在按钮。**

### 根因

`public/_headers` 里写着手工 CSP：

```
Content-Security-Policy: ... script-src 'self' ...
```

**而 Astro 默认把页面脚本内联进 HTML。** 于是浏览器把**每一个内联脚本都拒了**：

```
Executing inline script violates the following Content Security Policy
directive 'script-src 'self''. Either the 'unsafe-inline' keyword,
a hash ('sha256-FQ1mRsQNvUOg6MrMrVEUwZxn1ZocuDlfm+aho0...'), ...
```

> **站上每一个交互都是死的。Menu 只是唯一一个看得见的实例。**

**而没有任何东西报过它**：构建成功、四道闸门全过、部署成功、sitemap 正常。
**那条控制台错误只在浏览器里才出现。**

### 排查过程：静态方法全部指向"代码是对的"

| 查了什么 | 结论 |
| --- | --- |
| `Nav.astro` 的处理器 | 绑定正确，选择器匹配 |
| 线上实际脚本字节 | 230 字节，逻辑正确 |
| CSS 媒体查询 | `<=900px` 时按钮 `inline-block`、列表 `display:none`、`[data-open=true]` 时 `flex`——**全对** |
| 几何 / 层叠 / z-index | 按钮中心点上方就是按钮本身，无遮挡 |
| 把处理器跑在 DOM stub 上 | 点击 → toggle 正常 |

**静态全对，所以我用无头浏览器 + DevTools 协议在 390px 视口真点了一次**：

```
我们的探针在同一击上响了 1 次   → 点击确实落在按钮上
data-open 仍是 false            → 站内自己的监听器根本不存在
控制台：[error] Executing inline script violates ... 'script-src 'self''
```

### 修法：让 Astro 生成 CSP

**Astro 7.3.5 有 `security.csp`**——它给每个内联脚本算 sha256 并写进 meta 标签。**手写的 CSP 不可能知道这些哈希。**

```js
security: {
  csp: {
    algorithm: "SHA-256",
    directives: ["default-src 'self'", "img-src 'self' data:", "form-action 'self'", "base-uri 'self'"],
    styleDirective: { resources: ["'self'", "'unsafe-inline'"] },   // Shiki 用内联样式属性
  },
}
```

**并把 `_headers` 里手写的 CSP 删掉**——**两个策略会取交集，旧的更严，留着就等于没修。**

**踩到的坑**：`script-src` / `style-src` **不能在 `directives` 里设**（Astro 报 `Did not match union`），要放 `styleDirective`；而 `styleDirective.resources` **默认不含 `'self'`**。

**另外把 `frame-ancestors` 从 meta 挪到 `_headers`**——浏览器**忽略 meta 里的该指令**，且每次加载都警告。

### 补上本该有的自检：`tools/check-csp.mjs`

**已接进 preflight**：

```
[ ok ] csp    RESULT: PASS — every page's policy permits the scripts it ships
```

**逻辑**：对每个构建出的页面，把内联脚本逐个算 sha256，确认 `script-src` 里有它。

> **这个检查本该存在。它的缺失换来的是：一个静默失效的交互层，而构建、闸门、部署、sitemap 全都报成功。**

**这个检查我写了三遍才对，三次都是同一个错误——在引号上耍聪明**：CSP 值用双引号包着、内部全是单引号（`'self'`、`'unsafe-inline'`），所以 `[^"']*` 在 `'self'` 的开引号处就停，只抓到 12 个字符。**前两版把 36 个页面全报成坏的，而浏览器其实跑得好好的。**

### 线上实测（最终）

```
菜单点击   → open="true" · display:flex · 10 个链接全部可见
再点一次   → open=false
我们自己脚本被拦的次数 → 0
控制台剩余 → 1 条：Cloudflare 自己注入的 Web Analytics beacon（第三方，非本站代码）
```

## 一之四十、★ 文章页在手机上被截断——每篇都是（2026-10-07）

### 用户报的问题

> 手机端打开网页里面的文章看不全，需要在下面左右滑动才能看全文章。不是自适应的效果。电脑上屏幕大能看全。

**复现了。而且每一篇文章都是，其他页面却没问题。**

### 根因：CSS Grid 的 `min-width: auto`

**在真浏览器里量出来的**，不是读 CSS 猜的：

```
div.container   w=390   grid-template-columns: 1fr 300px
main#main       w=576   min-width: auto          ← 关键
pre             w=576   whiteSpace: pre
```

> **Grid 子项默认 `min-width: auto`——它拒绝缩到小于自己的内容。**
> **而文章内容里有 `<pre>` 算式块，`<pre>` 默认 `white-space: pre`、不换行。**
> **于是最长的算式那行决定了 `main` 的宽度，`main` 决定了页面宽度，页面就撑破了视口。**

**首页和计算器没有 `<pre>`——这正是为什么它们没事，也是为什么它看起来像"文章的问题"。**

### 三处修复，缺一不可

| # | 修法 | 作用 |
| --- | --- | --- |
| 1 | `.container > * { min-width: 0 }` | **这是真正的 bug**——恢复"允许收缩"的权限 |
| 2 | `.prose pre` / `.prose table` **原本完全没有样式** | 现在限宽在栏宽内、**内容在自己的盒子里横向滚动**（这是唯一该出现横向滚动的地方） |
| 3 | `html, body { max-width: 100%; overflow-x: hidden }` | 兜底：**今后任何一个宽元素都不该让整页长出滚动条** |

### 实测

```
本地构建  320px 与 390px × 12 个页面 → 0 溢出
线上      320px 与 390px × 7 个页面  → 0 溢出
          <pre> 实测：width=342  overflowX=auto  maxWidth=100%
```

### 补上自检：`tools/check-mobile.mjs`（已接进 preflight）

```
[ ok ] mobile layout    PASS - all 35 pages fit 320px and 390px with no sideways scroll
```

**它真的开浏览器、在 320px 和 390px 两个宽度下走完 dist/ 里全部 35 页**，任何一页 `scrollWidth` 超过视口就失败。
**没有 Chrome/Edge 时它会 SKIP 并警告**——缺浏览器不该挡住部署，但也绝不能静默通过。

**代价：preflight 从 ~30 秒变成 88 秒。** 一天跑一次，可接受。

### ★ 我自己的测量错了一次，值得记下

**第一次量的时候移动菜单是开着的**，它的链接贡献了一个 **226px 宽**的元素，**而那个数字正好等于溢出量**——于是"菜单"看起来就是元凶。

**重测时显式把菜单关掉、并断言它的状态**，才拿到真答案。
**另外一个线索**：`main` 的宽度每篇文章都不一样（592 / 576 / 488）——**这说明是内容在决定宽度，而不是某条样式规则。**

## 一之二、播客（2026-10-06 定案，取代路线图 §5.3 首段）

**路线图 §5.3 原文写的是"文章 → TTS → 分发"，即文章朗读。这个写法被推翻。**

**定案的两个形态必须分清**：

| 形态 | 定位 | 内容来源 | 声音 |
| --- | --- | --- | --- |
| **站内语音** | 文章朗读（辅助） | 文章原文 | TTS |
| **播客** | **原创节目**（独立内容线） | **另写，不是文章** | **TTS 双主播** |

### 为什么是双主播，以及我在这里犯的错

**我最初建议"不抄双主播"，理由是"两个声音，成本翻倍"。这个理由是错的**：

```
edge-tts 实测：322 个声音，英文 47 个
  en-US 男 9 / 女 8 · en-GB 男 2 / 女 3 · en-AU、en-CA、en-IE、en-IN 各有
```

**用 TTS，第二个声音的边际成本是零。** 真正的成本是**写对话脚本**，而那笔成本单主播也要付。

> **我又犯了一次同一个毛病**：**没先测就下结论。** 和之前"检查写错却怪文章"是同一类。**教训：否决一个方案之前，先测它成本最高的那一环。**

### 形态：反向访谈（不是闲聊）

- **主讲（分析师）**：讲事实和数字
- **提问者**：**替听众提问**，允许在数字出现时打断（"百分之五十的什么？"）

**为什么不抄闲聊式双主播**：两个人都不提供信息增量、靠笑声填空的形态，对我们这种"一个规则 + 一笔账"的内容不适用。**模仿的是"一问一答"的结构，不是"两个人聊天"的氛围。**

**声音搭配（样音用的）**：`en-US-AndrewNeural`（主讲）+ `en-GB-SoniaNeural`（提问）。**跨口音听起来不像同一套 TTS 出来的**——这是最便宜的调节杆。

### 已生成

```
build/podcast/sample-two-host.mp3    54.6 秒 · 143 词 · 157 词/分
tools/podcast-sample.py              生成脚本（10 轮对话，可换声音）
```

### 待你听的判断 + 未决

1. **样音能不能用**（你的耳朵决定）
2. **托管**：音频进 R2（$0，零出网费）vs 进仓库（会持续膨胀 git）。**RSS feed 建议放主域 `/podcast/feed.xml`**，因为**播客目录里的 feed URL 提交后几乎不能改**
3. **`edge-tts` 的授权风险**：它是反编译 Edge 朗读功能的库，**免费但非官方商用接口**，微软随时可能改端点。**建议先用，做起来后再换成有授权的接口**（Azure Speech / 火山 / 阿里）
4. **播客在漏斗里的位置**：**它帮订阅，不帮 UV**（路线图 §5.3 的判断是对的）。**"几十万订阅"需要它，"上百万 UV"不需要。**

### E. 跨产品 SOP 的采纳原则

2026-10-03 收到一份中文日更视频 SOP（抖音/视频号，党政手册风）。**采纳结论**：

| 采 | 不采 |

### F. 一个关于"看产物"的教训

### C10. 用行号猜法律条款归属 —— 我差点让你"更正"一个不存在的错误

## 七、怎么维护这个文件

**每次做完一件事，问三个问题：**

1. **数字变了吗？** → 更新第一节快照
2. **踩新坑了吗？** → 加进第四节，写清症状和解法
3. **有新待办或完成旧待办吗？** → 更新第五节
