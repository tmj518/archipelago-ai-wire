### ★★ 对标学习第 1 条已实施：`/instrument/<slug>/`（2026-10-08）

**第 1 条是"把每一个数据单元做成独立可路由的 URL"，被标为最高价值。**
**而我实施它时，实测把原始做法推翻了。**

#### 实测数据（先量再做）

```
207 条 figure 记录 → 199 个不同数据点     复用率 1.04x
被 ≥2 篇文章引用的                         8 个（其中 4 个是同一篇内的重复）
被 ≥3 篇文章引用的                         0 个
```

**→ 逐 figure 建页 = 199 个"页面里只有一个数字"的薄页。**

#### 改成文书层，因为同一份数据指向另一个答案

```
同样 207 条 figure，只来自 131 份文书（平均 1.58 个/份）
供出 ≥2 个数字的               35 份
被 ≥2 篇文章引用的              7 份
排除 25 个"Landed Math 模型"来源（那是我们的算术，不是外部文书）
→ 生成 28 页，覆盖 90 条 figure
```

#### ★ 而这一条里最值钱的判断是：

> **OWID 的可引用单元不是"数字"，是"数字来自的那份东西"。**
>
> **我量了两次才看出来**：先量 figure 层（1.04x，太薄），再量文书层（1.58x，可做）。
> **如果只量一次就动手，会做出 199 个薄页。**

#### 实施结果（实测）

```
构建        66 页（之前 36 → +30）
新页面      28 个 /instrument/<slug>/ + 1 个索引
覆盖        90 条 figure
sitemap     63 URL（23 文章 + 29 instrument）
每页验证    恰好 1 个 Dataset JSON-LD · 0 个 WebPage 冲突 · ≥1 反向链接 · 恰好 1 个 h1
```

**而页面是生成的不是手写的**：

```
node tools/build-instruments.mjs          生成注册表 src/data/instruments.json
node tools/build-instruments.mjs --check  检查与文章是否同步（preflight 会跑）
```

> **判据**：**页面数量跟着数据走，不需要有人编辑清单。**
> 后续文章从同一文书取更多数字、跨过深度阈值时，**页面自动出现**。

#### 诚实的部分

**`/instrument/` 索引页显式写着**：

> Documents that supplied a single figure are not listed here yet — **a page holding one number is not worth a URL.**

**78 份单数字文书留在外面，等数据说话。** 这既是给读者的说明，也是给我们自己的约束记录。

## 零之二、★★ 三条来自外部核验的规则（2026-10-08 吸收，已规则化）

> **来源**：外部核验文件 `LandedMath_整合版_v4.0` 第四部分「我自己的三处错误」。
> **这三条值得吸收，因为它们不是"要注意"的空话，而是各自带着可执行的判据。**

### 规则 1：不得用"常识"冒充"实测"

**它的错误**：把**海关总署**列为"L1 高频源，每天抓 2 次"——**而它整站 412**。
**成因**：凭常识判断"部委官网应该能抓"，**没有实测可达性**。

> **★ 规则**：**任何写进"抓取清单"的 URL，必须先跑一次可达性实测。未实测的必须标注「未实测」。**

**★ 而我在同一天犯了同一类错**：外部文件把 `stats.customs.gov.cn` 当"可查询的统计库"，
**我实测它 412**——**它是另一个子域，同一个反爬网关。**
**两个人都栽在"换个子域应该就行"这个常识上。**

**判据**：**清单里每个 URL 后面必须有实测状态（200 / 412 / 404 / 证书错），没有状态的视为未测。**

### 规则 2：不得因"搜了两次没找到"就下否定性强结论

**它的错误**：写过"**没有找到『外国读者看中国』这个模式的直接商业对标**"，
并据此把一个项目评分从 80% 压到 68%。**而 Sinocism 近 40 万读者、Substack 新闻类收入第一、做了 14 年。**

> **★ 规则**：**结论只能写成"在当前检索路径下未找到"，并写明检索词与次数。**
> **并且：否定性结论要主动反向验证一次（换语言、换平台、换关键词）。**

**判据**：**任何"没有 X"的结论，必须附检索词、次数、以及反向验证做过什么。**

### 规则 3：给任何项目提建议之前，先确认它的「当前状态」

**它最严重的错误**：在十几轮里反复说"0 篇、你还没开始、你从'想找项目'变成了'想完善文档'"。
**事实**：项目已在跑 V6.2——23+ 篇文章、Astro 站、7 项闸门、08:10 定时任务、四文件机制。

> **★ 规则**：**先确认「已有产出、已有机制、已定规则」，再决定建议的层级。**
> **——否则再多的分析也是错的，因为它答的不是对方的问题。**

**判据**：**提建议前先回答三个问题：现在有几篇产出？有哪些自动化机制？已定下哪些规则？**

## 一、这台机器上的编码规则（踩了 9 次）

**这是本项目最反复的一类坑。全部是同一个根因：**

> **Windows PowerShell 5.1 在中文系统上按 GBK（ANSI 代码页）读文件。**

### 规则

| 文件类型 | 必须 | 否则 |
| --- | --- | --- |
| **`.ps1`（PowerShell 脚本）** | **UTF-8 带 BOM + CRLF 行尾** | 脚本里的中文被解错 → **引号配对崩 → 报"字符串未终止"，而且指向一行完全正确的代码** |
| **`.bat`（批处理）** | **纯 ASCII**（文件名和内容都是） | cmd.exe 按 OEM 码页读，路径里的中文被误读 |
| **给 PowerShell 读的 UTF-8 文本** | 带 BOM | 中文变 `?????` |
| **Node/Python 读的文本** | 无所谓 | 它们按 UTF-8 正确解码 |

### 而第二条更隐蔽

**即使文件本身是好的，PowerShell 5.1 把管道给原生程序的文本按 ANSI 编码**：

```
中文指令 → 管道 → dsh  →  变成 "?????"
```

**修法**：在脚本最前面显式设：

```powershell
$utf8 = New-Object System.Text.UTF8Encoding $false
$OutputEncoding = $utf8                  # 管道给原生程序的编码
[Console]::OutputEncoding = $utf8        # stdout 编码
[Console]::InputEncoding = $utf8
```

### 验证方法（必须做）

**改完 .ps1 后，用解析器检查，而不是等它失败**：

```powershell
$e=$null
$null=[System.Management.Automation.Language.Parser]::ParseFile('路径.ps1',[ref]$null,[ref]$e)
if($e){$e|%{ "line $($_.Extent.StartLineNumber): $($_.Message)" }}else{"语法 OK"}
```

### ★★ 第 6 次：脚本里的中文文件名让定时任务当场死掉（2026-10-08）

**症状**：08:10 的定时任务 **Last Result = 2**（包装脚本的 FATAL），
**日志只有 8 行**：

```
task : NOT FOUND
FATAL task file not found at ...\鑷姩鍖朹姣忔棩浠诲姟.txt
                              ↑ "自动化_每日任务" 被当成 GBK 解出来
```

**两个原因叠加**：

1. **`tools/run-daily.ps1` 的 BOM 丢了**——**我上一次用 edit 工具改它时被去掉了**
2. **脚本正文里硬编码了中文文件名** `自动化_每日任务.txt`

**没有 BOM → PowerShell 5.1 按 GBK 读脚本 → 内嵌的中文文件名变乱码 → 找不到文件。**

**★ 而最阴险的是：手动跑能过，任务计划跑挂。**
**同一个文件、同一台机器、同样的字节，两个入口的解码方式不同。**

### 所以规则是「不变量」，不是「记得加 BOM」

> **凡是 Task Scheduler 要跑的 `.ps1`，正文必须纯 ASCII——包括注释。**
> **一个字节的含义都不该依赖编码。**
>
> **理由**：BOM 会被编辑工具弄丢（它确实丢了），而只要文件里没有 >0x7E 的字节，
> **不管按哪种编码解，含义都不变。**

**而中文文本可以留**——**放在独立的 `.txt` 里，用显式 UTF-8 读取**（`ReadAllText` + `Encoding.UTF8`）。

**改了什么**：

```
自动化_每日任务.txt        →  daily-task.txt          （文件名纯 ASCII）
tools/run-daily.ps1        →  正文纯 ASCII + BOM 恢复
tools/check-preflight.ps1  →  正文纯 ASCII（原来引用了已改名的 每日体检.bat）
DailyCheck.bat             →  早已是纯 ASCII
```

**验证方法**（每次都该跑）：

```js
const t = readFileSync(p, "utf8").replace(/^\uFEFF/, "");   // BOM 本身是 U+FEFF，要排除
const bad = [...t].filter((c) => c.charCodeAt(0) > 126);
```

### ★ 绝不做的四件事

1. **绝不用 PowerShell 的 `Get-Content` / `Set-Content` 往返读写含非 ASCII 的源代码文件。**
   **我这样做过一次，把一个闸门文件（`tools/serp-check.mjs`）弄成了无效 UTF-8 并推送到了生产。**
   要用 Node 读写。
2. **绝不用 PowerShell 的 `>` 重定向读 git blob 或二进制。** 它会写成 UTF-16，**让每个版本看起来都是坏的**（我因此误判过 7 个提交全是坏的）。
3. **绝不用 PowerShell 的 `-e` 内联跑含引号、反引号、`$` 的 Node 代码。** PowerShell 会先吃掉它们。
   **写临时 `.mjs` 文件跑，再删。**
4. **绝不在要定时跑的 `.ps1` 里写任何非 ASCII 字符**（见上）。

| 场景 | 做法 |
| --- | --- |
| 复杂的 Node 代码 | **写文件**（`node xxx.mjs`），不要 `node -e "..."` |
| 复杂的 PowerShell | **写文件**，不要 `-Command "..."` |
| **改源文件里的一个字符串** | **用 edit 工具，绝不用 `(Get-Content -Raw) -replace ... \| Set-Content`**——见下面第 7 次踩坑 |
| **要写多行 commit message** | **写到 `.git/COMMIT_MSG_TMP.txt`，`git commit -F`，提交后删**——**绝不写到仓库根目录**，见第 9 次踩坑 |
| **commit message 里有引号** | **绝不用 `git commit -m "..."` 内联**——PowerShell 会把引号切碎成参数。**用 `-F` 传文件** |
| 需要同时看 stdout/stderr 的退出码 | **不要用 `*>&1`**——会把原生命令的 stderr 变成 `NativeCommandError` 并可能中断 |
| 捕获原生命令输出并记日志 | **用 `Add-Content -Encoding UTF8`**，**不要用 `Tee-Object -Append`**（它写 UTF-16，日志变乱码） |
| 子进程捕获输出 | 沙箱内**命名管道被禁**，`child_process` 的默认 `stdio: 'pipe'` 会 EPERM。用 `stdio: 'inherit'` 或重定向到文件 |

### ★★ 第 9 次：commit message 文件被 `git add -A` 扫进版本库（2026-10-08）

**同一个错我犯了两次，第二次才知道原因。**

**事情经过**：

```
1. 写 MSG70.txt 到仓库根目录（因为要写多行消息）
2. git add -A          ← 把它扫进暂存区
3. git commit -F MSG70.txt   ← 提交了，里面包含 MSG70.txt 自己
4. Remove-Item MSG70.txt     ← 从磁盘删掉
5. git status          →  " D MSG70.txt"
   ↑ git 只看到"删除了一个被跟踪的文件"，而这一步没再提交
```

**结果：仓库里留下一个已提交但磁盘上不存在的文件，工作区永远有 1 项未提交。**

**★ 而这条规则其实早就写在本文件里了**：

> **"`write` 工具写 `.git/COMMIT_MSG_TMP.txt`，再 `git commit -F` 该文件，提交后删除"**

**我又没照做——因为写到根目录更顺手。**

### 规则（具体到可执行）

| 要做什么 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 写多行 commit message | **写到 `.git/COMMIT_MSG_TMP.txt`** | 写到仓库根目录 |
| 提交 | `git commit -F .git/COMMIT_MSG_TMP.txt` | `git commit -m "多行..."`（PowerShell 切碎引号） |
| 清掉 | `Remove-Item .git/COMMIT_MSG_TMP.txt` | 忘了，或删了却没重新提交 |
| 检查 | **`git status --porcelain` 必须为空** | 以为删了文件就干净了 |

> **★ 为什么 `.git/` 是对的**：**git 不跟踪 `.git/` 里的任何东西**，
> 所以 `git add -A` 永远扫不到它，第 2 步那个坑从根上不存在。

**★ 而"引号"那个坑是同一轮里的第二个**：commit message 里有一句 H1 带双引号，
`git commit -m "...H1 "Keep up with tech in 5 minutes"..."` 被 PowerShell 切成十几个参数，
报 `pathspec 'Keep' did not match any file(s)`。**用 `-F` 传文件，这个问题也不存在。**

**验证方法**：

```powershell
git status --porcelain    # 必须为空
git log --oneline -1      # 确认提交进去了
```

## 四、验证的纪律（这一条救过很多次）

### 规则 1：**改完要读回确认，不能信"命令成功了"**

**踩过**：一次 edit 的 `old_string` 我打错了，**替换静默地什么都没做，而命令报告成功**。我差点据此宣布修好了。

**做法**：编辑后**重新读那个位置**确认。

### 规则 2：**"报告成功"和"真的发生了"不是一回事**

- `schtasks /Create` 报成功，**但 `WorkingDirectory` 是空的**（我只在事后 `Query /XML` 才发现）
- 飞书写入报 `created 22, failed 0`，**但我回读才确认 22 行真的在**
- `git push` 报成功，**但线上的页面可能还在部署窗口里**

**做法**：**关键写入之后回读**；**关键操作之后独立核实**。

### 规则 3：**部署窗口内单次读取不算数**

**踩过**：线上核实报了一个 `404`，而页面其实已经在服务了。**只是我读在了部署中间态。**

**做法**：**重试到确认**（5 次 + 递增等待），**并用本地 `dist/` 对照**。

### 规则 4：**测试要能证明它会失败**

**一个检查在干净的输入上通过，什么都没证明**——它可能只是永远不触发。

**做法（本项目的标准做法）**：**注入该规则针对的那个缺陷，确认它会响、严重级对、退出码对，然后还原并重跑确认恢复。**

**示范**：给审核智能体注入 4 个缺陷，**4/4 全部抓到**——而且我发现其中一次"抓不到"其实是**我的注入没生效**，所以后来每次注入都**先在磁盘上验证突变已写入**。

### 规则 5：**表格数据必须按表格解析，不能先剥标签再用正则**（2026-10-09 新增）

**踩过**：美国联邦公报的关税费用表在剥掉标签后，`$34.58` 变成 `9 34`——**脚注编号 `9`、空格、然后 `34.58` 被从中间截断**。我据此得出"最低 MPF 从 $9.34 涨到 $34.58，涨了 3.7 倍"，**差一步就写进文章当标题**。

**五次尝试才拿到真相**：

| 尝试 | 结果 | 错在哪 |
| --- | --- | --- |
| 1. 剥标签 + `\$[\d,]+` 抓所有金额 | `9 34` | 以为 `9` 是整数部分 |
| 2. 位置规则（空格=小数点或千分位） | 两个年份都读成 `10` | 脚注编号混进去了 |
| 3. 「行内最后一个数字」 | 抓到脚注编号 | 脚注在值后面 |
| 4. 表格单元 `<tr>/<td>` 解析 | **`9` 是脚注，真值 `34.58`** | ✅ 对 |
| 5. 查 FY2025/FY2026/FY2027 三年 | `32.71 → 33.58 → 34.58` | 三年都是常规通胀 2.7–3.0% |

**规则**：

> **凡是从 HTML 取的结构化数据（费用表、税率表、统计表），必须先按 `<tr>`/`<td>` 解析单元，再取值。**
> **剥标签后的文本只用于人和关键词搜索，绝不用于取数字。**

**判别信号（出现任一条就说明你在错的路线上）**：

- 数字里出现**孤立的小整数**（`9`、`11`、`12`）紧挨着真正的大数字 → **那是脚注编号**
- 同一个字段在两个年份读出来**一模一样** → 你读到的是标签不是值
- 一个字段的变化幅度**远超通胀**（本项目里是 3.6 倍，而实际年调是 3%）→ **先怀疑解析，再怀疑世界**

**为什么这条值钱**：这类错误**不会让闸门变红**。数字格式完全合法、来源标注真实、`figures` 数组结构正确——**闸门全绿而文章是假的**。唯一能防住它的是**交叉核对**：我把 `$9.34` 拿去和 FY2025 的公告对，才发现那个数字在任何一年都不存在。

### 规则 6：**数字会传播，单位不会**（2026-10-10 新增）

**踩过**：印尼对聚乙烯防水油布的保障措施税，**中文源在同一个页面上，一段写"13,400 印尼盾/公斤"，下一段写"13,400 印尼盾/吨"**——**同一组四位数，相差一千倍。**

**WTO 为此专门发过更正件**：

```
G/SG/N/8/IDN/35/Corr.1   +   G/SG/N/10/IDN/35/Corr.1     2026-10-06
"This corrigendum is issued to reflect the correct heading of Table 7..."
Table 7. The Proposed Safeguard Measure
Specific Duty (Rupiah/kg)        ← 单位是【每公斤】
Period I    Period II   Period III
13,400      12,391      11,458
```

**如果按"每吨"读**：`13,400 ÷ 17,881 ÷ 1000 = 每公斤 0.0007 美元`——**读者会当成"可忽略"而不再管它**。真实是**每公斤 0.75 美元**，一条 4×6 米、200 gsm 的油布（4.8 公斤）**摊到 3.60 美元**。

**规则**：

> **抄数字时必须连单位一起抄，而且单位要去【签发机关的原件】核，不能去任何摘要核。**
> **判据：如果换算出来的金额小到"不像一个税"，先怀疑单位，再怀疑世界。**

**判别信号**（出现任一条就说明你在抄摘要而不是抄原件）：

| 信号 | 含义 |
| --- | --- |
| **同一页面上同一个数字出现两种单位** | 摘要在原件的两种版本之间来回抄，**两个都不能用** |
| 换算后的税额**小于货值的万分之一** | 没有海关会写一个会被四舍五入抹掉的税 |
| 原件里有一个**只为改表头而发的更正件** | 说明这个单位的坑**连官方都踩过**，你更要核 |
| **从价百分比与单位税额并存** | 两者是同一措施的两种表述（见下），**没有决议本体就不要选** |

**★ 同一天踩到的另一形态（秘鲁陶瓷马桶）**：

```
中文源：税额 5.7 / 14.3 / 12.7 / 14.3 【美元/个】
秘鲁官方（INDECOPI 新闻稿）：倾销幅度 45.2% / 45.2% / 26.8% / 45.2% 【从价】
```

**两者是同一措施的两种表述**（单位税额 ≈ 从价幅度的等值换算）。**我拿不到决议本体（El Peruano 被墙、PDF 拉不到），所以按规则 C 不用它做主数据**——**改用印尼那条，因为 WTO 更正件把单位钉死了。**

**为什么这两条合起来值钱**：**它们证明"多语言信息差"不是抽象说法，而是一个可以让买家错判一千倍的具体的坑。** 而这恰好是本项目存在的理由——**中文源发布、英文买家看不懂、摘要抄错单位**。**要做的不是翻译，是把单位和金额一起核到原件。**

### 规则 8：**测量的初始状态必须已知**

### 规则 9：**内链的判据是"已发布"，不是"文件存在"**（2026-10-11 新增）

**踩过**：写 #26 时我给一条内链指向 `eu-anti-dumping-cellulose-ethers-30-days`——**我核了"文件在不在"，它在（2620 字节），我就当成有效内链。**

**闸门判它 broken。我第一反应是"文件明明在，是 link-check 错了"。**

**真相**：那篇是 `draft: true`，**正文是 `<!-- SAMPLE POST: skeleton placeholder, replace before launch. -->`，一共 7 篇这样的骨架稿。** `link-check` 读的是**构建产物**，草稿不构建，所以链接指向一个不存在的页面。

**规则**：

> **校验内链目标，要读目标的 `draft` 与 `publishDate`，不能只判断文件存在。**
> **`src/content/blog/*.md` 里有 7 篇 skeleton，文件名看起来和正式文章完全一样。**

**为什么会错**：**"文件存在"是一个比"该页会被构建"更弱的条件，而我用了弱的那个还觉得够了。** 这和规则 1（改完要读回确认）是同一个毛病的不同形态：**用了一个便宜的代理指标，而它测的不是要测的东西。**

**做法（可复用）**：核对内链时跑一句读 frontmatter 的命令，把 `draft: true` 全部列出来；而不是 `Test-Path`。

### 规则 10：**HTTP 200 比 404 更危险，当它不带内容的时候**（2026-10-11 新增）

**踩过**：WTO 文件网关 `docs.wto.org/dol2fe/Pages/SS/directdoc2.aspx` 对我试的每一个文号都返回 **HTTP 200**，而响应体是 **2179 字节、不是 PDF 的东西**。

**若只看状态码，这是"成功"。** 而它意味着：**我一个字都没读到，却会以为我读到了。**

**规则**：

> **取一份文献时，状态码只证明"服务器答话了"。必须再验一次内容形态**——
> **PDF 要看文件头是否 `%PDF`；JSON 要能 `parse`；HTML 要看正文长度是否合理。**

**同一类的三个形态（本轮全部遇到，全部记进 `/unreadable.json`）**：

| 形态 | 例子 | 判别 |
| --- | --- | --- |
| **200 但无内容** | WTO 文档网关返回 2 KB 非 PDF | **最危险**：任何状态检查都读成成功 |
| **412 反爬** | `www.customs.gov.cn` 连根路径都 412 | 站点在，只是拒绝自动读；换入口可解 |
| **连不上** | `docs.eaeunion.org` / `eec.eaeunion.org` 从本网络超时 | **可能是地理性的**——写清楚"从我这边连不上"，而不是"该文件不存在" |

**做法**：**把这三类分开记录并公开**（`data/unreadable.json` + `/unreadable.json`），因为**读者需要知道的是"哪些数字我核不到第二来源"，而不是"我遇过几个错误"。**

**为什么这两条合起来值钱**：**它们都是"闸门全绿也抓不到"的错**——规则 9 是闸门抓到了而我不信它；规则 10 是闸门根本没在看。**规则 9 的教训是"别用便宜的代理指标"，规则 10 的教训是"状态码不是内容"。**

### 规则 11：**字数档位由表格的形态决定，不由题目的性质决定**（2026-10-11 新增）

**踩过**：填 `how-to-tell-a-factory-from-a-trading-company` 的骨架时，正文 **1,818 词**，被闸门 BLOCK：

```
✗ prose 1000-1800 words (no cost table)   1818 words
```

**我明明写了成本表**（断点那张表），**但闸门不认它是成本表。**

**查明 `hasCostTable` 的判据**：**表格行里含金额（`$` / `¥` / `CUR` + 数字）的必须 ≥3 行。** 我那张表只有 **2 行**——于是整篇被判为"无成本表"，上限从 2,500 掉到 1,800。

**规则**：

> **闸门按【正文里有没有 ≥3 行含金额的表格行】自动判定档位，不看你写的是不是成本题。**
> **所以"这篇是成本题"不构成任何豁免——表格行数不够，就是无成本表档。**

**做法**：写成本题时**先数表格行**。三行是档位门槛，不是内容门槛——**把 2 行的表补到 3 行，比删 200 词更符合"完成度优先"**（删词是削内容，补行是加内容）。

**为什么这条值钱**：**它反直觉。** 一篇讲押金风险的文章，读者和作者都会认为它是成本题，**而闸门只看表格形态。** 这与规则 1、9、10 是同一族：**判据挂在可测量的形态上，而人会误以为它挂在意图上。**

### 规则 12：**改文章的一节时，不要用"到下一个 `##` 为止"的正则**（2026-10-16 新增）

**踩过**：`#31` 的 AI Summary 写了 174 词（要求 60–100），我用这个正则去截：

```js
/## AI Summary\n\n[\s\S]*?\n\n(?=Vietnam's Ministry)/
```

**它匹配成功了——然后删掉了 AI Summary 之后的三段正文**，包括开篇段和"定义块"引用块。

**原因**：`[\s\S]*?` 是惰性的，但 `(?=` 的锚点如果**在更远的地方**，正则就一路回溯到那里。我以为它停在"下一个 `##`"，实际它停在"我恰好写进 lookahead 的那句话"。

**规则**：

> **要替换一节的正文，用两个已知标题的字符串下标做切片，不要用正则找"节的结尾"。**
> **"下一个标题"在正则里不是一个可靠的概念——`(?=\n##\s|$)` 的 `|$` 会让它匹配到文件末尾。**

**做法**：

```js
const i = t.indexOf("## AI Summary");
const j = t.indexOf("## What happened");
t = t.slice(0, i) + NEW_SECTION + t.slice(j);
```

**为什么这条值钱，以及它为什么排在这条线上**：闸门**确实会抓到**这次删除——定义块是硬要求，删了它就 BLOCK。
**但那是删除之后。** 而闸门抓到的是**症状**（缺一个节），不是**原因**（一次越界替换），
所以我第一反应会是"补一个引用块"，而不是"我的正则在删东西"。

**这与规则 7 是同一族**：`静态检查找不到的问题，要真的开浏览器`。
**这里是它的镜像**：*检查器抓到了症状，但抓不到原因——所以症状出现时，先问"是谁改的"，再问"缺了什么"。*

### 规则 13：**闸门对目录型输入只哈希文件名列表——所以它可能拿旧 dist 下判断**（2026-10-16 新增）

**踩过（第二次，第一次我误判了）**：preflight 报

```
[FAIL] mobile layout   RESULT: FAIL | 320px /instrument/european-commission-.../
                       scrollWidth=404 (table +71px, thead +71px, tr +71px)
```

**第一反应是"某个 instrument 页的表格在 320px 溢出"——一个真实缺陷。**
**而单跑 `node tools/check-mobile.mjs` 是 PASS，而且它数到 135 页，闸门只报 131 页。**

**★ "页数对不上"就是判据**：闸门拿的不是当前的 `dist/`。

**根因（读源码，不猜）——★ 比我第一版写的更严重**：

```js
// 修复前 gate.mjs 的目录分支
if (st.isDirectory()) {
  for (const f of readdirSync(abs).sort()) {
    try { h.update(f).update(readFileSync(join(abs, f))); }   // 读的是【顶层条目当作文件】
    catch { h.update(f + ":unreadable"); }                     // 子目录全部走这里
  }
}
```

**`dist/` 的顶层是目录而不是文件**（`blog/`、`instrument/`、`topic/`、`category/`、`_astro/`、sitemap…），
**所以每一个条目都落进 `catch`，只贡献了自己的名字。`dist/` 的哈希因此几乎恒定。**

→ **后果：mobile layout 与 CSP 这两道以 `["dist"]` 为输入的闸门，可以用旧构建的判定。**

```
实测（2026-10-16，两次）
  preflight 报：320px /instrument/european-commission-.../ 表格 +71px 溢出
  preflight 报：390px /blog/china-rare-earth-.../ 代码块 +87px 溢出
  而单跑 check-mobile：135 页全部 PASS
  ★ 判据是页数：闸门说 131 页，单跑说 135 页
```

**规则**：

> **凡是输入写 `["dist"]` 的闸门，结果都可能来自旧构建。**
> **判据不是"结果对不对"，是"页数对不对"——闸门报的页数与 `check-mobile` 单跑报的页数不一致就是脏缓存。**
> **临时绕法：`node tools/gate.mjs --fresh`。**

**已修（2026-10-16）**：`hashPaths` 的目录分支改为**递归遍历**，并且**把相对路径与内容一起入哈希**（这样文件改名也失效）。
验证是双向的——**只证明"改了会失效"不够，还得证明"没改仍命中缓存"**：

```
第 1 次（冷）         208s
第 2 次（应命中）       1s   ← 缓存仍生效，没变慢
改一个 dist 页面后    204s   ← ★ 修复前这里会是 1s
```

**为什么这条排在这条线上**：**它与规则 1（读回）、规则 10（200 不等于有内容）同族——判据挂在"可测量的形态"上，
而"目录"这个形态不含内容。** 而它比规则 10 更隐蔽：**报告出来的是一条具体的 CSS 缺陷（表格 +71px、代码块 +87px），
看起来像布局问题，而它其实是缓存问题。** 一个有经验的读者会去修表格，而不是去清缓存。

### ★ GitHub 的写路径会整个坏掉（2026-10-07 23:10 实测）

**症状**：`git push` 一律失败，报 `remote: Internal Server Error`（HTTP 500），**而所有读操作正常**。

**诊断方法（照做，不要瞎试）**：

| 测试 | 它回答什么 |
| --- | --- |
| `git ls-remote origin main` | **读路径**——成功就说明网络和认证都没问题 |
| `git push origin HEAD:refs/heads/push-test` | **写路径**——推一个空分支，排除内容因素 |
| `githubstatus.com/api/v2/status.json` | GitHub 自己怎么说 |

**实测结论**：

```
git ls-remote origin main                  →  成功（读正常）
git push origin main                       →  失败，Internal Server Error
git push origin HEAD:refs/heads/push-test  →  同样失败（空分支！）
githubstatus.com                           →  All Systems Operational
待推送内容                                  →  6 个文件 / 151 KB / 最大 84 KB
```

> **定性：这个仓库的写路径在 GitHub 侧故障。**
> **连一个空分支都推不上去 → 与内容、体积、我们这边的一切都无关。**

**规则**：

1. **不要重试超过 3 次**——每次都是同一个服务端错误，浪费时间和配额
2. **本地 commit 是安全的**——**先提交，后推送，永远是这个顺序**，推不上去不丢东西
3. **把「待推送」的 commit 数量和 hash 写进报告**，然后继续做下一件事
4. **区分两种失败**（包装脚本已能自动分辨）：
   - `Internal Server Error` / `remote rejected` → **GitHub 侧**，等它恢复，**别动任何配置**
   - 连接超时 / 无法解析主机 → **多半是加速器**，那才是要检查的
5. **这类故障通常几十分钟到几小时内自愈**，定时任务每天都会再试
   → **最坏情况是延迟一天上线，不是丢失**
