# 发布安全门槛与回滚方案

> 2026-10-27 · 第 3 轮
> 状态：**门槛清单 + 现状矩阵**。矩阵里的每一格都以仓库中的实际文件为依据；没有实现的项目标"缺失"，不用空壳补齐。

## 一、四层状态的定义

| 标记 | 含义 |
|---|---|
| **已实现** | 有代码/闸门，且**有测试或实跑证据**在拦截 |
| **部分实现** | 有机制但覆盖不全（如只拦部分情况，或需人工执行） |
| **仅文档约定** | 写在规范里，没有任何机器执行 |
| **缺失** | 连约定都没有，或约定与实现不一致 |

## 三、必须修的三处（按风险排序）

### R1｜`main` 上的 push 等于发布（最高风险）

现在没有分支保护，也没有"仅 CI 通过后合并"的限制。发布权限与写代码权限是同一个权限。

**建议（需在 GitHub 设置中执行，本轮不做）**：
- `main` 开启分支保护：要求 PR、要求 CI 通过、禁止强推；
- 内容生成流程改为 **PR 模式**：自动流水线只开 PR，合并由人点。

### R2｜重复运行无幂等键

当前"是否已发布"靠文件名推断。同一选题重跑会生成同名文件，覆盖旧内容而不留痕。

**建议**：`lib-llm` 与生成流程引入 `run_id`，写入文章 frontmatter 与 `logs/usage.jsonl`。这一步同时解决"单篇成本不可计算"（见 `docs/成本与数据资产审计_2026-10-27.md`）。

### R3｜`link-check` 的盲区

它只走"已构建页面之间的链接"。一个指向**从未生成的路由**的链接不会被判为 broken（`/tracker/` 就是这样漏过去的）。

**建议**：增加一条规则——所有以 `/` 开头的 `href` 必须能在 `dist/` 找到对应文件；找不到即 broken。**这是加强，不是放宽。**

## 四、回滚方案

### 代码回滚（本地可执行）

| 场景 | 动作 | 验证 |
|---|---|---|
| 单个提交有问题 | `git revert <sha>`（不使用 `reset --hard`） | 重跑 build + 10 闸门 + 全部测试 |
| 想回到更早状态 | 检查 `...\_备份\archipelago-repo-cmdNN-*.bundle`，`git clone <bundle>` 到临时目录比对 | 克隆内跑测试 |
| 文章内容错误 | 改 frontmatter + 正文，`updatedDate` 记录修订 | `qa-check` + 重新构建 |

### 线上回滚（需控制台，本轮未验证）

| 场景 | 动作 | 无法自动化原因 |
|---|---|---|
| Pages 部署了坏版本 | Cloudflare Pages → Deployments → 选中上一个成功部署 → Rollback | 需要账户权限，仓库内无 token |
| 域名/DNS 异常 | Cloudflare DNS 控制台 | 同上 |
| 需要"下线"某篇文章 | 删除内容文件 → push → 重建 | 依赖 R1 的权限链 |

**已知限制**：从未演练过线上回滚。第一次演练应安排在首次正式发布**之前**，否则"回滚方案"只是文档。
