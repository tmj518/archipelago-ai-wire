## 第三步：这一轮做什么（★ 三步固定顺序）

**核心循环**（做法 C：不依赖外部、先提升已有质量）：

```
1. 复查 reviewBy 最近到期的一篇
   → 对照它引用的一手来源重读（读原文，不读二手转述）
   → 有实质变化 → 公开更正（写进 revisions 与 updatedDate）
   → 无实质变化 → 明确记录「无需改动」，绝不只改日期
   ★ 更正与"无需改动"都【不】算作当天的新增

2. 从 信源清单.md 选一个来源和一个栏目
   → 优先本周【篇数最少】的栏目（平票时选历史上总量最少的）
   → 若某栏目是 0 篇，必须先补它
   → 优先查省级与目的市场来源（信息增量最高）
   → 海关总署的数字走 http://english.customs.gov.cn/ 或财政部关税司替代

3. ★ 写一篇新文章（净新增），编号 = 当前 articleNumber 最大值 + 1
   ★ 完成度优先于字数——见第四步的两档字数上限
```

**每周上限 15 篇净新增**（5 栏目 × 3）。**若本周已达 15 篇，当天只做第 1 步，并在报告里说明已达上限。**

**★ 而闸门不变，这才是关键**：**"不做产量路线"禁的是"为产量牺牲质量"，不是"每天发"。**
**每天一篇约束的是节奏，不是标准——而完成度优先于字数。**

**写新文章时优先只用仓库里已核实的数字**（不读新文件），那样最省。要写新事实时才读一次文献。

**编号**：新文章取当前 `articleNumber` 最大值 +1，写进 frontmatter。

### ★★★ 三条硬规则（2026-10-09 新增）——比闸门更严，因为它们挡的是"假"

**闸门能挡格式，挡不住"格式完全合法而数字是错的"。这三条挡的是后者。**

**规则 A：表格数据必须按表格解析。**
从 HTML 取结构化数据（费用表、税率表、统计表）时，**先按 `<tr>`/`<td>` 解析单元，再取值**。
**剥标签后的纯文本只用于人读和关键词搜索，绝不用于取数字。**

判别信号（出现任一条就说明你在错的解析路线上）：

| 信号 | 含义 |
| --- | --- |
| 数字里出现**孤立的小整数**（`9` / `11` / `12`）紧挨着真正的大数字 | **那是脚注编号** |
| 同一字段在两个年份读出来**一模一样** | 你读到的是标签不是值 |
| 某字段的变化幅度**远超通胀**（比如 3.6 倍，而年调是 3%） | **先怀疑解析，再怀疑世界** |

> **2026-10-09 实例**：美国联邦公报费用表剥标签后 `$34.58` 显示为 `9 34`。
> 我读成 `$9.34`，得出"最低 MPF 涨了 3.7 倍"——**差一步写进文章当标题**。
> 真相：`9` 是脚注编号，值就是 `34.58`；三年为 `32.71 → 33.58 → 34.58`，全是常规通胀 2.7–3.0%。
> **四次解析失败，只有读 `<tr>`/`<td>` 得到正确值。** 已写进 `经验与踩坑记录.md` 第四节规则 5。

**规则 B：每个数字都要交叉核对到第二份文件。**
**一个数字只有一个来源时，你无法区分"数字是真的"和"你读错了"。**
读到的费率 / 税率 / 日期，去**上一年度的同类公告**、或**规则本体**（eCFR、19 CFR、HTSUS）核一遍。
做不到交叉核对时，**在 `How confident` 里明说"单一来源，未交叉核验"**。

**规则 C：不许把推断写成事实，也不许编造数字。**
非事实论断标【推断】或【观点】。
**报告里的每个数字，都要能指回一个文件或一次命令的输出。**

> **2026-10-09 实例**：我编过一个 `$50.79`（把手续费差额与担保费相加），
> **CBP 从未公布这个数**——发布前自查时删掉了。**这类数字不会让闸门变红。**

### ★ 结构 V6.2（2026-10-08 改：两个新增节 + 两档字数）

**★ 字数分两档，按文章有没有成本表自动判定**（闸门会检表格里的金额，不用声明）：

| 题型 | 目标 | 上限 |
| --- | --- | --- |
| **带成本表**（有每件/每柜/每吨金额表） | **1,200–1,800 词** | **2,500** |
| **不带成本表** | **1,200–1,600 词** | **1,800** |

**下限统一 1,000 词。**

> **★ 用户定的规则原话（2026-10-08）**：
> **"不管字数多少，内容完整度，满足用户搜索意图和文章有价值才是核心。"**
>
> **所以上限是用来防注水的，不是防覆盖的。** 带成本表的题有结构下限——
> 实测：4 张表格 + 定义块 + 计算节 + callout ≈ 450 词的非叙述内容，
> 加上三问 FAQ 和 `How confident`，**真实下限在 1,950 词左右**。
>
> **而证据一致**：Backlinko 的 1,180 万搜索结果**发现字数与排名无直接关系**，首屏均值 1,447 词。
> **长度是"完整性"的症状，不是目标。**

**每节的词数预算**：

| 段 | 预算 | 说明 |
| --- | --- | --- |
| **AI Summary** | 60–100 | **结论先行**：判断是什么 + 对谁意味着什么 |
| `## What happened` | 200–300 | 精确数字 + 政策原文 |
| `## Why now` | **100–200** | ★ **压这里**——它与 What happened 重叠最多 |
| `## So what` | 250–350 | **护城河：判断 + 成本测算。不要砍它** |
| **`## How confident`** | **100–180** | ★★ **新增节，见下** |
| `## For you` | 150–250 | ≥3 组分人群建议 |
| `## The data point` | 60–100 | 一句话 + `<div class="callout">` |
| `## How we calculated this` | 50–120 | 算式 |
| `## FAQ` | **240–400** | **3 问**（旧要求 3–5 问）。**这是最大的一块，要压就压这里** |

**压缩顺序**（不够短时按此顺序砍）：`Why now` → `FAQ` 减到 3 问 → `What happened`。
**绝不砍**：`So what` 的成本测算、`How we calculated this`、`How confident`。

### ★★ 新增节一：`## How confident`（区分事实/推断 + 反面论证）

**这是这个站唯一没人做的东西。** 所有免费来源（官方外宣、自媒体）都只说一面。

**必须包含三部分，缺一不可**：

```markdown
## How confident

**已确认（有原始文献支撑）**
- 一句一条，每条挂一个 figure 或具名来源

**推断（我的判断，证据不直接支撑）**
- 一句一条，并说明推断依据什么

**什么情况下我会错**
- 如果 X 发生，这个判断不成立
- 如果 Y 数据被修正，成本数字会变
```

**为什么要它**：Google 的 QRG 把"可核验"列为可信度核心，而**"承认局限"是所有免费来源都不写的**。
**它看起来在削弱结论，实际在建立信任——而且它必须放在正文前部，不是末尾**，
因为 NN/g 的眼动数据显示 **57% 的注意力在第一屏、74% 在前两屏**。

### ★★ 新增节二：事实 / 推断 / 观点必须分开

**默认是"已确认"**（因为有五元组撑着）。**只在不是事实时才标**：

| 标注 | 什么时候用 |
| --- | --- |
| **（不标）** | 有 figure 或一次文献支撑的数字与陈述 |
| **【推断】** | 你的判断，证据不直接支撑（例如"这意味着下季度会涨"） |
| **【观点】** | 价值判断，无对错 |

**★ 绝不允许把推断写成事实。** 那正是这个站要区别于自媒体与官方外宣的地方。

### 其余硬性要求（不变）

- frontmatter 长度：`title` ≤120、`subtitle` ≤160、`description` ≤300 字符。**超一个字符整个构建会失败，全站页面会掉回上一次部署。**
- `figures` ≥5 条，每条必须有 `value` / `unit` / `period` / `source` / `retrieved` 五项。
- `sources` ≥3 条，必须是一次文献（法规、公报、海关公告、Federal Register、EUR-Lex 等），不是二手报道。
- 正文至少一个带金额的每件/每柜/每吨成本表，且**必须调 `tools/` 里的模型**，不许即兴算术。
- 禁止模糊词：`may` / `might` / `possibly` / `perhaps` / `could` / `reportedly` / `allegedly`（月份 `May` 首字母大写不受限）。
- `AI Summary` **60–100 词**（V6.2 放宽，为了容纳"对谁意味着什么"；旧要求是恰好 40–60）。
- 必须有 `## How we calculated this`，把算式写出来。
- 每篇至少 1 条对外正文内链，**且不得形成 A→B 与 B→A 的环形对**。
- 每个数字都要能追到来源；查不到就写「查不到」，**不要编**。
- **不要写第一人称体验**（"I have run this play twice"），零人工审稿下那只能是编的。

## 第五步：交付（你负责到本地 commit 为止）

**★ 闸门只跑一遍，在所有编辑做完之后。用这一个命令：**

```
node tools/gate.mjs
```

**它一次跑全部 7 项闸门，且带缓存**：

```
第一次（或改了很多文件后）  约 2–4 分钟   ← serp-check 抓竞品页 + 移动端开浏览器
之后同一天再跑              约 0–1 秒     ← 按输入哈希命中缓存
```

**实测：改一篇文章之后再跑全部闸门 = 1 秒。**（之前是 5.5 分钟，而那 5.5 分钟里 81% 是重复联网抓同一批竞品页。）

**所以：**

- **不要**每改一处就重跑闸门。**攒到全部改完，跑一次 `node tools/gate.mjs`。**
- **不要**分别手跑 qa-check / reviewer-check / serp-check —— `gate.mjs` 一次全跑，并行了那几项快的。
- `--fresh` **只在需要强制重算时用**（例如怀疑缓存不对）。**默认不要用。**
- 竞品页缓存 **24 小时**过期 → 隔天第一次跑会真抓，之后走缓存。

**★ 若本轮写了新文章，先重建文书注册表**（`/instrument/` 页面由它派生）：

```
node tools/build-instruments.mjs
```

**它会写入 `src/data/instruments.json`，preflight 会检查它与文章是否同步。**
**新文书跨过深度阈值（供出 ≥2 个数字，或被 ≥2 篇文章引用）时会自动多出页面，不需要手写。**
**排除规则**：`Landed Math <模型名>` 来源是我们的算术不是外部文书，会被排除。

**① `description` 必须 ≤ 300 字符。**
超了 **Zod schema 直接拒绝，`astro build` 失败，全部页面下线**。
闸门跑在构建之前，**所以它不会先告诉你**。写完立刻量一次字符数。

**② 至少 3 条指向其它文章的正文内链。**
`link-check` 会把零内链的文章判为 **orphan**（爬取图上等于不存在），闸门 FAIL。
**★ 而内链有词数成本：3 条约 90 词。初稿就要写到 2,400 以内，否则加内链时会突破 2,500 上限。**

### ★★ 提交收录与搜索监测（自动化）

**★ 先说清楚哪条能做、哪条不存在**：**Google 没有普通文章的收录提交 API。**
Indexing API 只对 JobPosting 与 BroadcastEvent 生效，**拿它提交文章违反谷歌政策**。
**"请求编入索引"那个按钮只能人工点，不能脚本化。**

**能自动化的两条**：

```
node tools/submit-urls.mjs --changed      # 提交今天的 URL 给 IndexNow（必应 + Yandex）
node tools/gsc-report.mjs                 # 拉搜索数据，给每篇文章一个动作
```

| 工具 | 做什么 | 需要什么 |
| --- | --- | --- |
| **`submit-urls.mjs`** | 读 sitemap 里 `lastmod` 是今天的 URL，POST 给 IndexNow；日志写 `logs/submissions.jsonl` | **已配好**（密钥在 `public/<key>.txt`，已托管） |
| **`gsc-report.mjs`** | 按规格 §8 给每篇文章判定动作（改标题 / 优化 / 保持 / 回选题池），输出 `data/gsc/` | **需要服务账号密钥** `gsc-service-account.json` + 把服务账号邮箱加进 GSC 用户权限 |
| **`prove-automation.mjs`** | **端到端验证整条链（12 项）**；`--submit` 会做一次真实提交 | 无需凭据 |

**★ 怀疑自动化断了时，跑这条**：

```
node tools/prove-automation.mjs --submit
```

**它检查 12 项**：文章是否都进 sitemap · 每 URL 是否都有 lastmod · **日期是否内容派生而非构建派生** ·
提交是否选中今天的 URL · 密钥是否托管 · 真实提交是否被接受 · 是否写日志 · 分析步骤是否不崩 ·
两步是否接进包装脚本 · 是否不能让运行失败 · 注册表是否跟上新文章。
**`preflight.mjs` 每次体检都会跑它，所以正常情况下不必手动跑。**

**★ Google 那边靠什么**：**sitemap 的 `lastmod`**——构建时自动写入，**74/74 条都有**，日期来自内容（`updatedDate` → `revisions` → `publishDate`），不是构建时间戳（构建戳会被 Google 忽略）。

**没凭据时 `gsc-report.mjs` 会明确列出要找的路径和五步配置方法，绝不假装有数据。**

**每周读一次 `data/gsc/report_*.md`**——**那是唯一不是猜的关键词数据来源**。

**`git add -A && git commit`** 在闸门全绿之后。

**推送、构建验证、线上核实由包装脚本接手。** 你只要保证本地 commit 是干净的。

`node tools/feishu-sync.mjs` 你也可以跑（走网络 API，不走命名管道）。

最后更新 `进度日志.md`。

## 第六步：报告（中文，必须含这六项）

0. **★ 今天的净新增是哪一篇** —— `新文章 #N <slug>`，**或明确说明"今天没写新文章 + 为什么"**
   （允许的原因只有两个：本周已达 15 篇上限，或确实找不到符合条件的题——后者要写清找了几条、为什么都不合格）
1. **编号与类型** —— `新文章 #N <slug>` / `更正 #N <slug>`（两者分开写，更正不算新增）
2. **这一轮做了什么**，含实测数字（闸门几过、改了哪些文件、reviewer 几条）
3. **还哪些没做完**，按等级（卡凭据的 / 我能独立做的 / 等用户决定的）
4. **需要用户给什么**（凭据或决定）
5. **成本**

**本周进度一行**：`本周净新增 X/15 篇 · 各栏目：trade-policy N · platforms N · supply-chain N · sourcing N · logistics N`

**一行格式**：`第 N 篇已提交 · 本周 X/15 · 闸门 Y/Z · 成本 ¥W · 缺：<一句话>`

## 出错时

**任何一步失败，不要跳过、不要假装成功。** 把失败原因和你的判断写进报告，然后停下。

**但不要为了让报告好看而绕过闸门。** 一道闸门红了就是红了——那是它在工作，不是它在碍事。

**也不要为了修那两项沙箱限制反复尝试**——它们是宿主级设置，从仓库里改不了，而包装脚本已经替你做了那两件事。
